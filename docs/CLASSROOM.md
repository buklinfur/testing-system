# Лента класса и ручные задания (модуль 4в)

Возможности в духе Classroom: лента класса, ручные задания, их сдача и ручная оценка с историей. Решение —
D-059 в [`DECISIONS.md`](DECISIONS.md): заменяет D-027 («виды элементов контеста»). Таблицы —
[`DATA_MODEL.md`](DATA_MODEL.md) («Изменения 4в.1»).

В модуле 4в есть модель, сервисы, правила доступа (чистые функции), админский API и judgectl. Эндпоинты ученика
появятся в 4б.2, интерфейс — в модуле 5.

| Где | Что |
|---|---|
| [`backend/app/models.py`](../backend/app/models.py) | `FeedItem`, `FeedItemAudience`, `AssignmentWork`, `AssignmentSubmission`, `AssignmentSubmissionFile`, `AssignmentReview` |
| [`backend/app/deadline_rules.py`](../backend/app/deadline_rules.py) | правила сроков, общие с задачами контестов |
| [`backend/app/extensions.py`](../backend/app/extensions.py) | продления сроков, общие с задачами контестов |
| [`backend/app/classroom/access.py`](../backend/app/classroom/access.py) | правила ленты, условия, сдачи — чистые функции (§6) |
| [`backend/app/classroom/grading.py`](../backend/app/classroom/grading.py) | переходы статусов, проверка оценки, публикация, вид для ученика — чистые функции (§4, §5) |
| [`backend/app/classroom/items.py`](../backend/app/classroom/items.py), [`works.py`](../backend/app/classroom/works.py) | сервисы: элементы, аудитория, ленты, продления; сдачи, оценки, возвраты, публикация (§7) |

## 1. Элемент ленты

Элемент (`feed_items`) — одна запись в ленте. Виды:

| `kind` | Что это | Сдача и срок |
|---|---|---|
| `contest` | ссылка на существующий контест (`contest_id`); контесты не дублируются | нет: окно, сроки задач и доступ решает сам контест |
| `assignment` | ручное задание: текст в Markdown (`body_md`), шкала оценки, вид ответа | есть: срок, политики после срока, продления, ручная оценка |
| `material` | материал библиотеки | нет; включается в 4в.4 (до тех пор запрещён `CHECK`) |

**Состояния** (`state`):
* `draft` — черновик, видят только админы;
* `published` — опубликован;
* `archived` — убран из ленты, но ученики по-прежнему видят свои работы.

**Отложенная публикация** — это `published` с будущим `available_from`. Планировщика нет: момент проверяется при
каждом запросе. До `available_from` (включительно с него) элемента у ученика нет вовсе — как у задачи контеста.

**Порядок в ленте** (4в.1) — по дате: `available_from`, а без него `published_at`; новые сверху. Темы-разделы ленты
обсуждаются вместе с вопросом В2 (Справочник) перед 4в.4.

## 2. Адресаты

`feed_item_audience` — группы и/или отдельные ученики; одна строка — один адресат.
* Лента группы — элементы, адресованные этой группе.
* Лента ученика — элементы его **текущих** неархивных групп и адресованные ему лично, без дублей.
* Состав группы считается на момент запроса, как у контестов (D-020): добавленный ученик видит элемент сразу,
  убранный перестаёт видеть, но **свою работу видит всегда**. Архивная группа ничего не даёт.
* Контест-элемент доступа к контесту **не выдаёт**: доступ решает контест (`access_mode`, `contest_groups`). Если
  группы аудитории к контесту не подключены, сервис предупреждает. Сам он группу к контесту не подключает: это
  противоречило бы `contest.yaml` и `apply` (К5).

## 3. Ручное задание

Настройки задаются на элементе:

| Поле | Значения | Смысл |
|---|---|---|
| `grading` | `points` (+ `max_points`), `pass_fail`, `none` | шкала: баллы 0…`max_points`; зачёт или незачёт; без отметки — только статус. Школьная «пятёрка» — это `points` с `max_points = 5`. Свободной текстовой оценки нет, её роль играет комментарий |
| `answer_kind` | `mark`, `text` (с 4в.3 — `files`, `text_or_files`) | `mark` — просто «сдано» (работа в тетради); `text` — текстовый ответ |
| `grades_release` | `manual` (по умолчанию), `immediate` | когда ученик видит оценку (§5) |
| `available_from`, `due_at`, `after_due_statement`, `after_due_submit` | как у задачи контеста (`CONTESTS.md` §1, §4) | границы: `available_from` и срок — включительно (D-032). Без срока задание принимает сдачи всегда, пока опубликовано |

**Сроки.** Сроки, продления, политики после срока и отметка `late` — **общие с задачами контестов**:
* чистые правила — [`deadline_rules.py`](../backend/app/deadline_rules.py);
* продления — [`extensions.py`](../backend/app/extensions.py), строка `deadline_extensions` с `feed_item_id`;
* время приёма — серверное, UTC, в момент получения запроса;
* `late` фиксируется при приёме и потом не пересчитывается.

Продление элемента должно быть позже `due_at` и позже `available_from`. Окна контеста и дорешивания у задания нет.

**Ответ.** Каждая сдача — новая неизменяемая запись (`assignment_submissions`); засчитывается последняя, остальные —
история. Текст ответа хранится файлом `answer.md` в блобах (`assignment_submission_files`); в 4в.3 та же таблица
примет загруженные файлы. В админском API 4в.1 текст отдаётся строкой в JSON карточки работы, скачивание файлов
появится в 4в.3. Отозвать сдачу ученик не может — вместо этого он сдаёт заново.

## 4. Работа и её статусы

Работа (`assignment_works`) — «папка» ученика по заданию, одна на пару «задание — ученик». Она создаётся первой сдачей
или первой оценкой.

Строку работы блокирует (`SELECT … FOR UPDATE`) **каждое** изменение: сдача, оценка, возврат, публикация. Поэтому
одновременные действия идут друг за другом.

`status` — кэш истории (`assignment_submissions` и `assignment_reviews`), пишется в той же транзакции; источник
истины — история.

| Статус | Когда |
|---|---|
| назначено | строки работы нет (не хранится) |
| `submitted` | последнее событие — сдача |
| `graded` | последнее событие — оценка |
| `returned` | последнее событие — возврат на доработку |

**Переходы:**
* назначено → сдача → `submitted`;
* `submitted` → новая сдача → `submitted`;
* `submitted` → `graded` | `returned`;
* `returned` → сдача → `submitted`;
* `graded` → переоценка → `graded` (история сохраняется);
* `graded` → `returned`;
* назначено → `graded` — оценить можно и без сдачи: работа в тетради, ноль за несданное.

Пересдать оценённую работу нельзя (`already_graded`), пока преподаватель её не вернёт.

Таблица переходов — `grading.next_status(статус, событие)`; события `submit`, `grade`, `return`, `release`.
Публикация (`release`) статуса не меняет. Остальные пары — отказ с кодом:

| Статус | Событие | Отказ |
|---|---|---|
| назначено | `return` | `nothing_to_return` |
| назначено, `submitted`, `returned` | `release` | `nothing_to_release` |
| `graded` | `submit` | `already_graded` |
| `returned` | `return` | `already_returned` |

Тест перебирает все 16 пар.

**Оценка по шкале** — `grading.check_grade`:

| Шкала | Оценка | Отказ |
|---|---|---|
| `points` | `score` в 0…`max_points`, `passed` пусто | `score_required`, `score_out_of_range`, `grade_kind_mismatch` |
| `pass_fail` | `passed` задан, `score` пусто | `passed_required`, `grade_kind_mismatch` |
| `none` | `graded` значит «принято», `score` и `passed` пусты | `grade_not_expected` |

**Публикация** — `grading.release_target` публикует текущую оценку (последнюю `graded`), один раз. Отказы:
* `release_not_needed` — задание с `immediate`;
* `nothing_to_release` — оценок нет;
* `already_released` — текущая оценка уже опубликована.

**Метки, а не статусы:**
* «сдано с опозданием» — `late` последней сдачи;
* «не сдано» — сдач нет и эффективный срок прошёл.

Обе — фильтры очереди проверки. Статуса «на проверке» нет.

## 5. Видимость оценки

Строки `assignment_reviews` только добавляются:
* `graded` — оценка;
* `returned` — возврат на доработку;
* `released` — публикация оценки, ссылка `release_of` на строку `graded`; одна публикация на оценку.

Текущая оценка для преподавателя — последняя `graded`.

Что видит ученик:
1. **`grades_release = manual`.** Видна последняя `graded`, у которой есть `released`. Если оценок с публикацией нет,
   оценки не видно.
2. **Переоценка после публикации не видна, пока её не опубликуют.** До этого ученик видит прежнюю опубликованную
   оценку.
3. **Возврат на доработку виден сразу** вместе с его комментарием. Прежние оценки остаются в истории.
4. **`grades_release = immediate`.** Видна последняя `graded`.
5. **`grading = none`.** «Принято» видно сразу при любом `grades_release`: скрывать нечего. Публикация отвечает
   `release_not_needed` (`grading.seen_at_once`).

**Статус, который видит ученик** (`grading.student_view`), — статус последнего события, которое ученику можно видеть:
* сдача — `submitted`;
* возврат — `returned`, с комментарием;
* оценка, которую можно видеть, — `graded`.

Неопубликованная оценка и сама публикация пропускаются. Поэтому:
* до публикации ученик видит «сдано»;
* после возврата и скрытой переоценки он видит возврат;
* после скрытой переоценки опубликованной оценки он видит прежнюю оценку.

Сервис передаёт события работы (сдачи и строки `assignment_reviews`) в том порядке, в каком они произошли. Даты
модуль не сравнивает.

Комментарий оценки и возврата — простой текст до 2000 символов. Как и текст ответа, он недоверенный: фронтенд
выводит его только как текст или через санитайзер (`ADMIN_API.md` §4.1).

## 6. Доступ

Чистые функции — [`classroom/access.py`](../backend/app/classroom/access.py) и
[`classroom/grading.py`](../backend/app/classroom/grading.py). Таблица случаев —
`tests/test_classroom_rules_units.py`.

**Чистота.** Модули:
* не обращаются к базе и сами не читают часы: `now` (серверное, UTC, момент получения запроса) передаёт сервис;
* импортируют только `deadline_rules` и `contests/access.py`;
* не сравнивают даты сами: вся арифметика сроков — в `deadline_rules`.

Тесты проверяют это разбором кода и импортом без SQLAlchemy.

**Что передаёт сервис:**
* аудиторию элемента и группы ученика — неархивные, в которых он состоит сейчас;
* продления (`extensions.due_moments`);
* статус работы;
* для контест-элемента — контест, участие и признак «в группе контеста».

Админ может всё, кроме сдачи работ. Для ученика:

| Функция | Правило |
|---|---|
| `in_audience` | адресован лично или через группу, в которой ученик **сейчас** состоит; архивная группа ничего не даёт |
| `item_listed` | элемент в ленте: `published`, `in_audience`, наступил `available_from` (включительно). У контест-элемента ещё `can_view_contest` **или** `can_see_own_results` из `contests/access.py`: своих правил контеста нет, доступ элемент не выдаёт. Черновика нет; архивного в ленте нет |
| `can_view_assignment` | условие задания: `item_listed` и не скрыто после эффективного срока при `after_due_statement = hidden`. Скрыто **и у ученика, у которого уже есть работа**, как у задач контеста; у архивного элемента тоже скрыто |
| `can_see_own_work` | своя работа (сдачи, статус, опубликованная оценка): всегда, если работа есть и элемент не черновик — без аудитории, после срока, при скрытом условии, в архиве |
| `can_submit_work` | см. ниже |
| `missing` | «не сдано»: сдач нет и эффективный срок прошёл |

`can_submit_work` проверяет по порядку — первая неудача даёт код:

| # | Код | Когда |
|---|---|---|
| 1 | `not_a_student` | сдаёт админ |
| 2 | `not_an_assignment` | элемент не задание |
| 3 | `not_published` | черновик |
| 4 | `item_archived` | элемент в архиве |
| 5 | `no_access` | ученик не в аудитории |
| 6 | `not_available_yet` | раньше `available_from` |
| 7 | `deadline_passed` | после эффективного срока при `after_due_submit = no`; при `late` сдача принимается с `late`, при `yes` — как обычная |
| 8 | `already_graded` | работа оценена и не возвращена |
| 9 | `answer_required` | `answer_kind = text`, а текст пуст |
| 10 | `text_not_expected` | `answer_kind = mark`, а текст прислан |
| 11 | `text_too_long` | текст больше лимита (`JUDGE_ASSIGNMENT_TEXT_MAX_KB`, по умолчанию 64 КБ в UTF-8) |

Принятая сдача — код `ok` или `late` (флаг `late`).

## 7. Сервисы

Сервисы — [`classroom/items.py`](../backend/app/classroom/items.py) (элементы) и
[`classroom/works.py`](../backend/app/classroom/works.py) (работы). Тесты — `tests/pg/test_classroom_pg.py`.

Общие правила:
* функции делают `flush`, но не `commit`: транзакцией владеет вызывающий (judgectl — одна на команду, API — одна на
  запрос);
* отказ — `FeedError` с постоянным кодом, вызывающий откатывает транзакцию;
* каждое действие преподавателя пишется в `audit_log`. Сдачи учеников в аудит не пишутся, как посылки.

**Элементы** (`items.py`):
* `create_item`, `update_item` — те же ограничения, что `CHECK` таблицы, но с кодами: `title_invalid`,
  `kind_not_available` (материал — с 4в.4), `contest_required`, `grading_invalid`, `max_points_invalid`,
  `answer_kind_invalid`, `deadline_invalid`, `item_invalid`. После первой оценки шкала (`grading`, `max_points`) не
  меняется — `grading_locked`. Новый срок или политика уже принятые `late` не пересчитывают.
* `publish` — нужен хотя бы один адресат (`no_audience`). `archive` — только опубликованный (`item_not_published`).
  `delete_item` — только черновик без работ и продлений (`item_not_draft`, `item_has_works`,
  `item_has_extensions`).
* `set_audience` (и `add_audience` / `remove_audience`) — группа только неархивная (`group_archived`; уже
  адресованная архивная остаётся), ученик только с ролью `student` (`not_a_student`); у опубликованного элемента
  хотя бы один адресат.
* `contest_warning` — для контест-элемента: группы аудитории, не подключённые к контесту, вход по коду, личные
  адресаты в режиме `groups`. Это только предупреждение: элемент к контесту ничего не подключает и доступа не выдаёт.
* `group_feed` — элементы группы для преподавателя, новые сверху. `student_feed` — лента ученика: его текущие
  группы и личная адресация, каждый элемент один раз, по `access.item_listed`. Эндпоинт ленты — в 4б.2.
* Продления элементов — `add_extension`, `list_extensions`, `remove_extension` поверх общего ядра `extensions.py`.
  Коды те же, что у контестов, плюс `not_an_assignment`. Аудит — `item.extension_add` / `item.extension_remove`;
  `contest.extension_*` не меняются.

**Работы** (`works.py`):

| Функция | Что делает | Отказы |
|---|---|---|
| `submit_work(db, user, item, now, text=…)` | сдача ученика сессии | коды `access.can_submit_work` |
| `grade_work(…, student, …, score / passed, comment, release)` | оценка; с `release` — сразу и публикация | шкала (§4), `not_published`, `not_addressed` (не адресат и работы нет), `not_a_student`, `comment_too_long` |
| `return_work(…, student, now, comment)` | возврат на доработку | `comment_required`, `nothing_to_return`, `already_returned` |
| `release_grades(…, item, now, students=None)` | массовая публикация | `release_not_needed` (для всего вызова) |
| `student_work(db, user, item, now)` | что видит ученик сессии | — |
| `work_detail(db, blobs, item, student, now)` | вид преподавателя: все сдачи с текстом, все записи проверки, кэш статуса, что видит ученик | — |

**Ответ.** Лимит `JUDGE_ASSIGNMENT_TEXT_MAX_KB` (по умолчанию 64, в КБ UTF-8) проверяется до записи блоба. Текст
сохраняется файлом `answer.md` через хранилище блобов, одинаковый текст — один блоб. `now` вызывающий берёт один раз,
до чтения тела запроса (D-041): сдача получает `created_at = now` и `late`, решённый в этот момент. Продление,
выданное позже, `late` не меняет.

**Блокировки.**
* Каждое изменение работы — сдача, оценка, возврат, публикация — берёт её строку `assignment_works` через `SELECT …
  FOR UPDATE` и решает по статусу, прочитанному под блокировкой.
* Первое изменение пары «задание — ученик» создаёт строку через `INSERT … ON CONFLICT (item_id, user_id) DO NOTHING`
  и затем блокирует её. Две первые сдачи одновременно дают одну работу и две сдачи; оценка без сдачи против первой
  сдачи — тоже одну работу.
* Массовая публикация блокирует работы в порядке `id`, поэтому две публикации не попадают во взаимную блокировку.

Тесты, каждый в двух соединениях:
* две первые сдачи;
* оценка без сдачи против первой сдачи;
* две оценки;
* сдача против оценки;
* публикация против переоценки;
* две массовые публикации.

**Кэш статуса** (`assignment_works.status`) пишется в той же транзакции, что и событие: это `grading.next_status`,
применённый к событию. После каждого сценария тест сверяет кэш с историей.

**Порядок событий.** `works.events` — один запрос с `ORDER BY at, вид, id`: сдача идёт раньше записи проверки
в тот же момент, записи одного вида — по `id`. Оценка с `release` в одной транзакции даёт две записи с одинаковым
`at`, и публикация остаётся после оценки. Сдача и оценка в один момент — оценка последняя. `grading.student_view`
получает события в этом порядке.

**Массовая публикация.**
* Публикует текущую оценку каждой работы элемента или только перечисленных учеников, в одной транзакции.
* Неподходящая работа пропускается и не валит весь вызов. Результат — по каждому ученику: `released` или причина —
  `nothing_to_release` (работы нет или она не оценена), `already_released`.
* Аудит — одна запись `work.release`.

**Личность.** Ученик приходит только объектом `User`: из сессии в 4б.2, из командной строки в judgectl. Работа
находится по паре (элемент, ученик); `work_id`, `user_id` и `submission_id` извне функции не принимают. Тест
проверяет, что ученик A не сдаёт, не читает и не получает статус по работе B.

**Связь с 4а.**
* `groups.why_kept_after_rollback` — группа в аудитории элемента считается использованной.
* `groups.archive` — пишет в аудит и элементы ленты группы (`groups.feed_items_of`). Ответ API и judgectl с ними —
  в 4в.1b.
* `users.traces` — следами считаются: созданные элементы, добавленные адресаты, личная адресация, работы
  и оценки.
* `dev_seed --item <id> [--text-file F]` (только `JUDGE_DEV=1`) сдаёт работу как ученик `dev-student-N` через
  `submit_work`, по тем же правилам; так smoke 4в.1b будет сдавать работы до 4б.2 (D-047).

## 8. Что крепится к этим сущностям позже

* **Комментарии (4в.2)** — `comment_threads` с ровно одной целью:
  - `feed_item_id` — общая ветка элемента;
  - `work_id` — личная ветка ученика и преподавателей по заданию;
  - при необходимости `contest_problem_id` с учеником.
* **Вложения (4в.3):**
  - файлы ученика — та же `assignment_submission_files`: снимается ограничение `answer_kind`, добавляются квоты и
    белый список типов;
  - файлы преподавателя к заданию — `attachments` с владельцем `feed_item_id`.
* **Материалы (4в.4)** — снимается `CHECK material_after_4v4`, добавляется ссылка на материал.
* **Сборщик блобов (модуль 6)** должен учитывать `assignment_submission_files`, иначе удалит ответы учеников.
