## 1. Элемент ленты

Элемент (`feed_items`) — одна запись в ленте. Виды:

| `kind` | Что это | Сдача и срок |
|---|---|---|
| `contest` | ссылка на существующий контест (`contest_id`); контесты не дублируются | нет: окно, сроки задач и доступ решает сам контест |
| `assignment` | ручное задание: текст в Markdown (`body_md`), шкала оценки, вид ответа | есть: срок, политики после срока, продления, ручная оценка |
| `material` | выкладка материала библиотеки (§11) группам и ученикам (`material_id`; с 4в.4, `CHECK material_link`) | нет: только отложенная публикация (`available_from`) |

**Состояния** (`state`):
* `draft` — черновик, видят только админы;
* `published` — опубликован;
* `archived` — убран из ленты, но ученики по-прежнему видят свои работы.

**Отложенная публикация** — это `published` с будущим `available_from`. Планировщика нет: момент проверяется при
каждом запросе. До `available_from` (включительно с него) элемента у ученика нет вовсе — как у задачи контеста.

**Порядок в ленте** (4в.1) — по дате: `available_from`, а без него `published_at`; новые сверху. Темы-разделы ленты
обсуждаются вместе с вопросом В2 (Справочник) перед 4в.4.

## 2. Адресаты

`feed_item_audience` — группы и/или отдельные ученики; одна строка — один адресат.
* Лента группы — элементы, адресованные этой группе.
* Лента ученика — элементы его **текущих** неархивных групп и адресованные ему лично, без дублей.
* Состав группы считается на момент запроса, как у контестов (D-020): добавленный ученик видит элемент сразу,
  убранный перестаёт видеть, но **свою работу видит всегда**. Архивная группа ничего не даёт.
* Контест-элемент доступа к контесту **не выдаёт**: доступ решает контест (`access_mode`, `contest_groups`). Если
  группы аудитории к контесту не подключены, сервис предупреждает. Сам он группу к контесту не подключает: это
  противоречило бы `contest.yaml` и `apply` (К5).

## 3. Ручное задание

Настройки задаются на элементе:

| Поле | Значения | Смысл |
|---|---|---|
| `grading` | `points` (+ `max_points`), `pass_fail`, `none` | шкала: баллы 0…`max_points`; зачёт или незачёт; без отметки — только статус. Школьная «пятёрка» — это `points` с `max_points = 5`. Свободной текстовой оценки нет, её роль играет комментарий |
| `answer_kind` | `mark`, `text`, `files`, `text_or_files` (последние два — с 4в.3) | `mark` — просто «сдано» (работа в тетради); `text` — текстовый ответ; `files` — файлы и/или ссылки, без текста; `text_or_files` — текст, файлы, ссылки, хотя бы что-то одно (§10) |
| `grades_release` | `manual` (по умолчанию), `immediate` | когда ученик видит оценку (§5) |
| `comments_enabled` | `false` (по умолчанию), `true` | пишут ли ученики в общую ветку (§9). У контест-элемента только `false`: там ученики не пишут никогда |
| `available_from`, `due_at`, `after_due_statement`, `after_due_submit` | как у задачи контеста (`CONTESTS.md` §1, §4) | границы: `available_from` и срок — включительно (D-032). Без срока задание принимает сдачи всегда, пока опубликовано |

**Сроки.** Сроки, продления, политики после срока и отметка `late` — **общие с задачами контестов**:
* чистые правила — [`deadline_rules.py`](../backend/app/deadline_rules.py);
* продления — [`extensions.py`](../backend/app/extensions.py), строка `deadline_extensions` с `feed_item_id`;
* время приёма — серверное, UTC, в момент получения запроса;
* `late` фиксируется при приёме и потом не пересчитывается.

Продление элемента должно быть позже `due_at` и позже `available_from`. Окна контеста и дорешивания у задания нет.

**Ответ.** Каждая сдача — новая неизменяемая запись (`assignment_submissions`); засчитывается последняя, остальные —
история. Текст ответа хранится файлом `answer.md` в блобах (`assignment_submission_files`); в 4в.3 та же таблица
примет загруженные файлы. В админском API 4в.1 текст отдаётся строкой в JSON карточки работы, скачивание файлов
появится в 4в.3. Отозвать сдачу ученик не может — вместо этого он сдаёт заново.

## 4. Работа и её статусы

Работа (`assignment_works`) — «папка» ученика по заданию, одна на пару «задание — ученик». Она создаётся первой сдачей
или первой оценкой.

Строку работы блокирует (`SELECT … FOR UPDATE`) **каждое** изменение: сдача, оценка, возврат, публикация. Поэтому
одновременные действия идут друг за другом.

`status` — кэш истории (`assignment_submissions` и `assignment_reviews`), пишется в той же транзакции; источник
истины — история.

| Статус | Когда |
|---|---|
| назначено | строки работы нет (не хранится) |
| `submitted` | последнее событие — сдача |
| `graded` | последнее событие — оценка |
| `returned` | последнее событие — возврат на доработку |

**Переходы:**
* назначено → сдача → `submitted`;
* `submitted` → новая сдача → `submitted`;
* `submitted` → `graded` | `returned`;
* `returned` → сдача → `submitted`;
* `graded` → переоценка → `graded` (история сохраняется);
* `graded` → `returned`;
* назначено → `graded` — оценить можно и без сдачи: работа в тетради, ноль за несданное.

Пересдать оценённую работу нельзя (`already_graded`), пока преподаватель её не вернёт.

Таблица переходов — `grading.next_status(статус, событие)`; события `submit`, `grade`, `return`, `release`.
Публикация (`release`) статуса не меняет. Остальные пары — отказ с кодом:

| Статус | Событие | Отказ |
|---|---|---|
| назначено | `return` | `nothing_to_return` |
| назначено, `submitted`, `returned` | `release` | `nothing_to_release` |
| `graded` | `submit` | `already_graded` |
| `returned` | `return` | `already_returned` |

Тест перебирает все 16 пар.

**Оценка по шкале** — `grading.check_grade`:

| Шкала | Оценка | Отказ |
|---|---|---|
| `points` | `score` в 0…`max_points`, `passed` пусто | `score_invalid`, `score_required`, `score_out_of_range`, `grade_kind_mismatch` |
| `pass_fail` | `passed` задан, `score` пусто | `passed_required`, `grade_kind_mismatch` |
| `none` | `graded` значит «принято», `score` и `passed` пусты | `grade_not_expected` |

**Запись баллов** — `grading.parse_points` (D-061): `score` и `max_points` приходят строкой или числом JSON
(`"4.5"`, `4.5`) и становятся `Decimal` через `str`, не через двоичную арифметику. Допустима только обычная запись с
точкой, не больше шести цифр до неё и двух после (столбцы `Numeric(8, 2)`: до `999999.99`, D-088). Больше знаков
(`4.555`), больше шести цифр (`1000000`), экспонента (`1e1`),
`NaN`, `Infinity`, `true` — отказ: `score_invalid` у оценки, `max_points_invalid` у задания. Отрицательный балл
записан верно, его отвергает диапазон (`score_out_of_range`, у `max_points` — `max_points_invalid`).

**Публикация** — `grading.release_target` публикует текущую оценку (последнюю `graded`), один раз. Отказы:
* `release_not_needed` — задание с `immediate`;
* `nothing_to_release` — оценок нет;
* `already_released` — текущая оценка уже опубликована.

**Метки, а не статусы:**
* «сдано с опозданием» — `late` последней сдачи;
* «не сдано» — сдач нет и эффективный срок прошёл.

Обе — фильтры очереди проверки. Статуса «на проверке» нет.

## 5. Видимость оценки

Строки `assignment_reviews` только добавляются:
* `graded` — оценка;
* `returned` — возврат на доработку;
* `released` — публикация оценки, ссылка `release_of` на строку `graded`; одна публикация на оценку.

Текущая оценка для преподавателя — последняя `graded`.

Что видит ученик:
1. **`grades_release = manual`.** Видна последняя `graded`, у которой есть `released`. Если оценок с публикацией нет,
   оценки не видно.
2. **Переоценка после публикации не видна, пока её не опубликуют.** До этого ученик видит прежнюю опубликованную
   оценку.
3. **Возврат на доработку виден сразу** вместе с его комментарием. Прежние оценки остаются в истории.
4. **`grades_release = immediate`.** Видна последняя `graded`.
5. **`grading = none`.** «Принято» видно сразу при любом `grades_release`: скрывать нечего. Публикация отвечает
   `release_not_needed` (`grading.seen_at_once`).

**Статус, который видит ученик** (`grading.student_view`), — статус последнего события, которое ученику можно видеть:
* сдача — `submitted`;
* возврат — `returned`, с комментарием;
* оценка, которую можно видеть, — `graded`.

Неопубликованная оценка и сама публикация пропускаются. Поэтому:
* до публикации ученик видит «сдано»;
* после возврата и скрытой переоценки он видит возврат;
* после скрытой переоценки опубликованной оценки он видит прежнюю оценку.

Сервис передаёт события работы (сдачи и строки `assignment_reviews`) в том порядке, в каком они произошли. Даты
модуль не сравнивает.

Комментарий оценки и возврата — простой текст до 2000 символов. Как и текст ответа, он недоверенный: фронтенд
выводит его только как текст или через санитайзер (`ADMIN_API.md` §4.1).

## 6. Доступ

Чистые функции — [`classroom/access.py`](../backend/app/classroom/access.py) и
[`classroom/grading.py`](../backend/app/classroom/grading.py). Таблица случаев —
`tests/test_classroom_rules_units.py`.

**Чистота.** Модули:
* не обращаются к базе и сами не читают часы: `now` (серверное, UTC, момент получения запроса) передаёт сервис;
* импортируют только `deadline_rules` и `contests/access.py`;
* не сравнивают даты сами: вся арифметика сроков — в `deadline_rules`.

Тесты проверяют это разбором кода и импортом без SQLAlchemy.

**Что передаёт сервис:**
* аудиторию элемента и группы ученика — неархивные, в которых он состоит сейчас;
* продления (`extensions.due_moments`);
* статус работы;
* для контест-элемента — контест, участие и признак «в группе контеста».

Админ может всё, кроме сдачи работ. Для ученика:

| Функция | Правило |
|---|---|
| `in_audience` | адресован лично или через группу, в которой ученик **сейчас** состоит; архивная группа ничего не даёт |
| `item_listed` | элемент в ленте: `published`, `in_audience`, наступил `available_from` (включительно). У контест-элемента ещё `can_view_contest` **или** `can_see_own_results` из `contests/access.py`: своих правил контеста нет, доступ элемент не выдаёт. Черновика нет; архивного в ленте нет |
| `can_view_assignment` | условие задания: `item_listed` и не скрыто после эффективного срока при `after_due_statement = hidden`. Скрыто **и у ученика, у которого уже есть работа**, как у задач контеста; у архивного элемента тоже скрыто |
| `can_see_own_work` | своя работа (сдачи, статус, опубликованная оценка): всегда, если работа есть и элемент не черновик — без аудитории, после срока, при скрытом условии, в архиве |
| `can_submit_work` | см. ниже |
| `missing` | «не сдано»: сдач нет и эффективный срок прошёл |

`can_submit_work` проверяет по порядку — первая неудача даёт код:

| # | Код | Когда |
|---|---|---|
| 1 | `not_a_student` | сдаёт админ |
| 2 | `not_an_assignment` | элемент не задание |
| 3 | `not_published` | черновик |
| 4 | `item_archived` | элемент в архиве |
| 5 | `no_access` | ученик не в аудитории |
| 6 | `not_available_yet` | раньше `available_from` |
| 7 | `deadline_passed` | после эффективного срока при `after_due_submit = no`; при `late` сдача принимается с `late`, при `yes` — как обычная |
| 8 | `already_graded` | работа оценена и не возвращена |
| 9 | `answer_required` | `answer_kind = text`, а текст пуст; `text_or_files`, а нет ни текста, ни файлов, ни ссылок |
| 10 | `text_not_expected` | `answer_kind = mark` или `files`, а текст прислан |
| 11 | `files_not_expected` | `answer_kind = mark` или `text`, а присланы файлы или ссылки (4в.3) |
| 12 | `files_required` | `answer_kind = files`, а нет ни файлов, ни ссылок (4в.3) |
| 13 | `text_too_long` | текст больше лимита (`JUDGE_ASSIGNMENT_TEXT_MAX_KB`, по умолчанию 64 КБ в UTF-8) |

Шаги 11 и 12 добавлены в 4в.3 между прежними; порядок прежних кодов не изменился. `can_submit_work` знает только
**число** файлов и ссылок (`attachments`); что это за файлы, проверяет потом `attachment_rules.check_hand_in`, а
квоту — `attachment_rules.quota_ok` (§10).

Принятая сдача — код `ok` или `late` (флаг `late`).

## 7. Сервисы

Сервисы — [`classroom/items.py`](../backend/app/classroom/items.py) (элементы) и
[`classroom/works.py`](../backend/app/classroom/works.py) (работы). Тесты — `tests/pg/test_classroom_pg.py`.

Общие правила:
* функции делают `flush`, но не `commit`: транзакцией владеет вызывающий (judgectl — одна на команду, API — одна на
  запрос);
* отказ — `FeedError` с постоянным кодом, вызывающий откатывает транзакцию;
* каждое действие преподавателя пишется в `audit_log`. Сдачи учеников в аудит не пишутся, как посылки.
* сервисы комментариев — §9 «Сервисы».

**Элементы** (`items.py`):
* `create_item`, `update_item` — те же ограничения, что `CHECK` таблицы, но с кодами: `title_invalid`,
  `material_required` и `material_archived` (элемент-материал, с 4в.4; прежний `kind_not_available` больше не
  выдаётся), `contest_required`, `grading_invalid`, `max_points_invalid`,
  `answer_kind_invalid`, `deadline_invalid`, `item_invalid`. Смена шкалы — одно правило для API и judgectl
  (`update_item`): `pass_fail` / `none` без `max_points` очищает его, с `max_points` не `null` — `max_points_invalid`;
  `points` без `max_points` — `max_points_invalid`. После первой оценки шкала (`grading`, `max_points`) не
  меняется — `grading_locked`. Новый срок или политика уже принятые `late` не пересчитывают.
* `publish` — нужен хотя бы один адресат (`no_audience`). `archive` — только опубликованный (`item_not_published`).
  `delete_item` — только черновик без работ и продлений (`item_not_draft`, `item_has_works`,
  `item_has_extensions`).
* `set_audience` (и `add_audience` / `remove_audience`) — группа только неархивная (`group_archived`; уже
  адресованная архивная остаётся), ученик только с ролью `student` (`not_a_student`); у опубликованного элемента
  хотя бы один адресат.
* `contest_warning` — для контест-элемента: группы аудитории, не подключённые к контесту, вход по коду, личные
  адресаты в режиме `groups`. Это только предупреждение: элемент к контесту ничего не подключает и доступа не выдаёт.
* `group_feed` — элементы группы для преподавателя, новые сверху. `student_feed` — лента ученика: его текущие
  группы и личная адресация, каждый элемент один раз, по `access.item_listed`. Эндпоинт ленты — в 4б.2.
* Продления элементов — `add_extension`, `list_extensions`, `remove_extension` поверх общего ядра `extensions.py`.
  Коды те же, что у контестов, плюс `not_an_assignment`. Аудит — `item.extension_add` / `item.extension_remove`;
  `contest.extension_*` не меняются.

**Работы** (`works.py`):

| Функция | Что делает | Отказы |
|---|---|---|
| `submit_work(db, user, item, now, text=…)` | сдача ученика сессии | коды `access.can_submit_work` |
| `grade_work(…, student, …, score / passed, comment, release)` | оценка; с `release` — сразу и публикация | шкала (§4, в том числе `score_invalid`), `not_published`, `not_addressed` (не адресат и работы нет), `not_a_student`, `comment_too_long` |
| `return_work(…, student, now, comment)` | возврат на доработку | `comment_required`, `nothing_to_return`, `already_returned` |
| `release_grades(…, item, now, students=None)` | массовая публикация | `release_not_needed` (для всего вызова) |
| `student_work(db, user, item, now)` | что видит ученик сессии | — |
| `work_detail(db, blobs, item, student, now)` | вид преподавателя: все сдачи с текстом, все записи проверки, кэш статуса, что видит ученик | — |
| `work_card(db, blobs, item, student, now)` | карточка пары для judgectl и API: `work_detail` + `missing`; адресат без работы — `status: assigned`, событий нет, `missing` и `student_sees` вычислены; не адресат без работы (и работа на **другом** элементе) — `None` (API: 404 `work_not_found`) | — |
| `review_queue(db, now, item=…, group=…, status=…, late=…, missing=…, cursor, limit)` | очередь проверки (D-060), ниже | `missing_needs_item` |

**Ответ.** Лимит `JUDGE_ASSIGNMENT_TEXT_MAX_KB` (по умолчанию 64, в КБ UTF-8) проверяется до записи блоба. Текст
сохраняется файлом `answer.md` через хранилище блобов, одинаковый текст — один блоб. `now` вызывающий берёт один раз,
до чтения тела запроса (D-041): сдача получает `created_at = now` и `late`, решённый в этот момент. Продление,
выданное позже, `late` не меняет.

**Блокировки.**
* Каждое изменение работы — сдача, оценка, возврат, публикация — берёт её строку `assignment_works` через `SELECT …
  FOR UPDATE` и решает по статусу, прочитанному под блокировкой.
* Первое изменение пары «задание — ученик» создаёт строку через `INSERT … ON CONFLICT (item_id, user_id) DO NOTHING`
  и затем блокирует её. Две первые сдачи одновременно дают одну работу и две сдачи; оценка без сдачи против первой
  сдачи — тоже одну работу.
* Массовая публикация блокирует работы в порядке `id`, поэтому две публикации не попадают во взаимную блокировку.

Тесты, каждый в двух соединениях:
* две первые сдачи;
* оценка без сдачи против первой сдачи;
* две оценки;
* сдача против оценки;
* публикация против переоценки;
* две массовые публикации.

**Кэш статуса** (`assignment_works.status`) пишется в той же транзакции, что и событие: это `grading.next_status`,
применённый к событию. После каждого сценария тест сверяет кэш с историей.

**Порядок событий.** `works.events` — один запрос с `ORDER BY at, вид, id`: сдача идёт раньше записи проверки
в тот же момент, записи одного вида — по `id`. Оценка с `release` в одной транзакции даёт две записи с одинаковым
`at`, и публикация остаётся после оценки. Сдача и оценка в один момент — оценка последняя. `grading.student_view`
получает события в этом порядке.

**Массовая публикация.**
* Публикует текущую оценку каждой работы элемента или только перечисленных учеников, в одной транзакции.
* Неподходящая работа пропускается и не валит весь вызов. Результат — по каждому ученику: `released` или причина —
  `nothing_to_release` (работы нет или она не оценена), `already_released`.
* Аудит — одна запись `work.release`.

**Очередь проверки** (`review_queue`, D-060) — страница `{items, next_cursor}`, новые сверху. Строка: элемент,
ученик, `work_id`, статус, число сдач, последняя сдача, `late` (последней сдачи), `missing`, текущая оценка
преподавателя (`score`, `passed`, `released` — видит ли её ученик).
* **С `item`** — все текущие адресаты (лично или через неархивную группу, в которой ученик сейчас) и все, у кого есть
  работа; без работы — `assigned`. Курсор — id ученика. `missing` считается для каждого с его продлениями
  (`access.missing`).
* **Без `item`** — только существующие работы по всем заданиям («что ждёт проверки»), курсор — id работы.
  `missing` без `item` — отказ `missing_needs_item`: у ученика без работы здесь нет строки.
* `group` — **текущие** члены группы (как у посылок, D-043); `status` — `assigned`, `submitted`, `graded`,
  `returned`; `late` — последней сдачи.

**Чтение для интерфейсов** (`items.py`): `items_query(group, kind, states)` — выборка для списков (API листает её
курсором по id, judgectl сортирует в порядке ленты); `item_detail(item)` — `item_summary` со всеми настройками,
контестом, адресатами по именам (`groups: [{id, name, archived}]`, `users: [{id, login, display_name}]`), числом
продлений и предупреждением. judgectl — [`JUDGECTL.md`](JUDGECTL.md) (`item`, `work`).

**Личность.** Ученик приходит только объектом `User`: из сессии в 4б.2, из командной строки в judgectl. Работа
находится по паре (элемент, ученик); `work_id`, `user_id` и `submission_id` извне функции не принимают. Тест
проверяет, что ученик A не сдаёт, не читает и не получает статус по работе B.

**Связь с 4а.**
* `groups.why_kept_after_rollback` — группа в аудитории элемента считается использованной.
* `groups.archive` — пишет в аудит и элементы ленты группы (`groups.feed_items_of`); `judgectl group archive`
  перечисляет их в stderr, ответ API — поле `feed_items` (4в.1b).
* `users.traces` — следами считаются: созданные элементы, добавленные адресаты, личная адресация, работы
  и оценки; с 4в.2 — написанные и удалённые комментарии и личные ветки ученика (отметки прочтения — не след,
  удаление пользователя стирает их; `DATA_MODEL.md` «Изменения 4в.2»).
* `dev_seed --item <id> [--text-file F] [--file F]... [--link URL [TITLE]]...` (только `JUDGE_DEV=1`) сдаёт работу
  как ученик `dev-student-N` через `submit_work`, по тем же правилам, лимитам и квоте (`Settings.files`, с 4в.3);
  так smoke сдаёт работы до 4б.2 (D-047, D-081).

## 9. Комментарии (4в.2)

Решения — D-072 (модель) и D-074 (правила); таблицы — [`DATA_MODEL.md`](DATA_MODEL.md) «Изменения 4в.2». У элемента
ленты две ветки:
* **общая** — одна на элемент, видна всем, кто видит элемент;
* **личная** — ученик и преподаватели, одна на пару «задание — ученик», только у заданий. Ученики друг другу лично не
  пишут: такой сущности нет.

Ветка появляется с первым комментарием. Комментарий не редактируется; удаление мягкое.

**Правила** — чистые функции [`classroom/comment_rules.py`](../backend/app/classroom/comment_rules.py) поверх
`access.py` (видимость элемента) и `deadline_rules.py` (даты); те же требования чистоты, что в §6. Таблица случаев —
`tests/test_comment_rules_units.py`: именованные случаи и полный перебор «положение ученика (в группе, лично, убран из
группы, группа в архиве, не адресат) × состояние × скрытое условие × флаг × вид элемента × автор».

Убранный из группы и ученик архивной группы для правил одинаковы: сервис передаёт `in_audience` по **текущим**
неархивным группам (как в §2), и оба не в аудитории.

Преподаватель читает всё и пишет везде, кроме черновика (`not_published`), в том числе в архивном элементе и при
выключенных комментариях; частота его не ограничивает.

### Общая ветка

| Функция | Ученик |
|---|---|
| `can_read_shared` | у задания — `access.can_view_assignment`: ветка — часть страницы условия и скрывается вместе с ним (после срока при `after_due_statement = hidden`); у контест-элемента и элемента-материала (4в.4) — `access.item_listed`. Черновик, архив, не адресат, раньше `available_from` — нет. Выключенный флаг ветку **не прячет**: прежние комментарии видны |
| `can_post_shared` | по порядку, первая неудача даёт код (таблица ниже) |

| # | Код | Когда |
|---|---|---|
| 1 | `not_published` | черновик (и для преподавателя) |
| 2 | `item_archived` | элемент в архиве |
| 3 | `no_access` | не в аудитории сейчас |
| 4 | `not_available_yet` | раньше `available_from` |
| 5 | `no_access` | ветку не видно: условие скрыто после срока, контест не виден |
| 6 | `comments_teacher_only` | контест-элемент: ученики не пишут **никогда** (обсуждение решений во время контеста); преподаватель пишет — объявления. Вопросы жюри — отложенная ветка задачи контеста, не эта |

| 8 | коды тела | ниже |

### Личная ветка

`can_read_private` — ученик видит только **свою**, только у задания и не в черновике:
* ветка уже есть — всегда, как свою работу (`can_see_own_work`): вне аудитории, после срока, при скрытом условии,
  в архиве;
* ветки нет — пока задание в его ленте (чтобы задать первый вопрос).

`can_post_private` — ученик, по порядку:

| # | Код | Когда |
|---|---|---|
| 1 | `no_access` | чужая ветка (второй замок: сервис и так берёт ученика только из сессии) |
| 2 | `not_an_assignment` | не задание (у контест-элемента личной ветки нет) |
| 3 | `not_published` | черновик |
| 4 | `item_archived` | элемент в архиве: читать можно, писать нет |
| 5 | `no_access` | не в аудитории сейчас (убран из группы, группа в архиве) |
| 6 | `not_available_yet` | раньше `available_from` |
| 7, 8 | коды тела, `rate_limited` | |

Срок, скрытое условие и `comments_enabled` писать в личную ветку **не мешают**: вопрос об оценке после срока — обычное
дело.

Преподаватель: `not_an_assignment`, `not_published`, `not_a_student` (адресат ветки — не ученик), `not_addressed` (не в
аудитории сейчас, и нет ни работы, ни ветки — как у `grade_work`), затем тело.

### Тело

`check_body` строже `CHECK` таблицы. Всё, что оно пропускает, база принимает: это проверяет
`tests/pg/test_comment_schema_pg.py` на краевых строках.

| Код | Когда |
|---|---|
| `comment_invalid` | NUL или одиночный суррогат: PostgreSQL их не хранит, без этой проверки был бы 500. Проверяется первым |
| `comment_required` | ничего видимого: пусто или только пробельные (любые Unicode), управляющие (`Cc`) и форматные (`Cf`) символы |
| `comment_too_long` | больше 4000 символов (кодовых точек, как `char_length`) |

Сверх `CHECK` (`body_not_blank` отвергает только пустое и пробелы, табуляции, переводы строк ASCII) правило отвергает
тела только из: NBSP (`U+00A0`), других пробелов Unicode (`U+3000` и т. п.), разделителей строк и абзацев
(`U+2028`, `U+2029`), невидимых форматных символов (`U+200B`, `U+FEFF`, метки направления), управляющих символов
(`ESC`, `BEL`).

Текст с видимыми символами принимается как есть: пробелы по краям, переводы строк, табы, HTML и Markdown, управляющие
символы внутри. Это недоверенные данные: в API они отдаются как есть, в judgectl — через `core.terminal_text` (D-062),
в модуле 5 — Markdown без сырого HTML и через санитайзер.

### Частота и удаление

**Частота** (`rate_ok`) — не больше `JUDGE_COMMENT_RATE_PER_MIN` (по умолчанию 10) комментариев ученика за 60 секунд.
* Считаются и удалённые: удалить и написать заново лимит не обходит.
* Сервис считает строки в базе; правило сравнивает число.
* Применяется к эндпоинтам ученика (4б.2); сервисы 4в.2 уже вызывают его.

**Удаление** (`can_delete`) — мягкое:
* ученик удаляет только своё, в ветке, которую видит сейчас; преподаватель — любое;
* порядок отказов: `no_access` (ученик ветку не видит), `not_your_comment`, `already_deleted`;
* удалённое ученикам не показывается вовсе, без заглушки (`visible_to`); преподаватели видят его с текстом, кто удалил
  и почему.

### Сервисы

[`classroom/comments.py`](../backend/app/classroom/comments.py), решение D-075; тесты — `tests/pg/test_comments_pg.py`.
Общие правила §7: `flush` без `commit`, отказ — `FeedError` с кодом.

**Кто действует.**
* Ученик — всегда объект `User` (сессии в 4б.2, командной строки в `dev_seed`). Функции ученика не принимают id
  ученика: личная ветка — всегда его собственная. Объект админа в функции ученика — отказ `not_a_student`.
* Преподаватель пишет как `audit.Actor`: админ веба или консоль (автор `NULL`, имя пользователя консоли — в аудите).
* Читает `User` (ученик или админ) или `CONSOLE` — читатель judgectl: видит как преподаватель, отметок прочтения
  не имеет.

| Функция | Кто | Что |
|---|---|---|
| `post_shared` | ученик | комментарий в общую ветку (`can_post_shared`) |
| `post_private` | ученик | комментарий в свою личную ветку (`can_post_private`) |
| `teacher_post` | преподаватель | в общую ветку или, с `student`, в личную ветку ученика; аудит `comment.post` |
| `delete_own` | ученик | удаляет своё; `deleted_by` в строке, без аудита |
| `delete_comment` | преподаватель | удаляет любое, причина до 200 символов (`reason_too_long`); аудит `comment.delete` |
| `shared_thread`, `private_thread` | все читатели | ветка по возрастанию id, страница до 200 (`after`, `next_after`) |
| `comment_card` | все читатели | один комментарий в том же виде, что в ветке, плюс элемент, ветка, её вид и ученик личной ветки; без проверки доступа — для ответа на только что написанный или удалённый комментарий (API, judgectl) |
| `mark_read`, `unread_count` | ученик, админ | отметка прочтения и число непрочитанного |
| `unread_by_item` | ученик, админ | `{id элемента: непрочитанное}` по общей и своей личной ветке — для ленты 4б.2 |
| `threads_query` | админ, консоль | входящие: ветки, новые сверху; фильтры `item`, `group`, `awaiting`, `unread`; курсор |

**Ветка создаётся только записью.** Первый комментарий вставляет строку ветки через
`INSERT … ON CONFLICT DO NOTHING` по частичному уникальному индексу и перечитывает её. Два первых комментария сразу
(из двух соединений) дают одну ветку. Чтение, отметки и счётчики строк `comment_threads` не создают. Отметка в
ветке без комментариев возвращает 0 и ничего не пишет.

**Частота.** Комментарий ученика:
1. берёт `pg_advisory_xact_lock(locks.COMMENT_RATE, id ученика)` раньше любого чтения;
2. считает его комментарии за последние 60 секунд, удалённые тоже;
3. пишет новый с `created_at` = тот же `now`, а не время базы: окно и строка — в одних часах.

Параллельные комментарии одного ученика считаются по очереди: из `limit + 1` одновременных принимается ровно `limit`.
Преподаватель блокировку не берёт.

**Не найдено.** Ветка, которую читатель не видит, — `thread_not_found`. Это и чужая личная ветка, и элемент не из
его ленты, и (для преподавателя) личная ветка ученика без адресации, работы и ветки. Комментарий, которого ученик
не видит, — `comment_not_found`, один ответ для всех причин: нет такого, в чужой или невидимой ветке, уже удалён.
`not_your_comment` получает только чужой комментарий, который ученик видит. Отказы записи — коды правил выше
(`no_access` и т. д.).

**Что видно.**
* Ученику: автор — `display_name` и признак «преподаватель» (консоль — «Преподаватель»), логина нет, своё помечено
  `mine`; удалённых нет вовсе.
* Преподавателю: всё, с логинами; у удалённого — когда, кем (или консолью) и почему.
* В обоих видах: `can_post` / `cannot_post` — может ли читатель писать сейчас (без учёта тела и частоты).

**Непрочитанное и отметки.**
* Непрочитанное — комментарии **других**, не удалённые, с id больше отметки читателя.
* Отметка у каждого своя, у каждого админа тоже. Ставится на последний видимый комментарий или на заданный `up_to`:
  комментарий этой ветки, видимый читателю, иначе `comment_not_found`.
* Отметка только растёт (`GREATEST`): более ранний `up_to` её не уменьшает.
* У консоли отметок нет: `mark_read`, `unread_count` и фильтр `unread` для `CONSOLE` — ошибка программы, не отказ.

**«Ждёт ответа».** Последний неудалённый комментарий ветки написал ученик. Если преподаватель удалит свой ответ, ветка
снова «ждёт ответа». Это производное значение, оно нигде не хранится. Фильтр `group` берёт личные ветки текущих
членов группы (D-043) и общие ветки элементов, адресованных группе.

**Аудит.**
* `comment.post` (элемент, вид ветки, ученик, длина) и `comment.delete` (элемент, вид ветки, ученик, автор, причина) —
  только для действий преподавателя и **без текста** комментария.
* Комментарии учеников в аудит не пишутся, как сдачи. Удаление учеником своего видно в строке (`deleted_by`).
* Флаг `comments_enabled` меняется через `update_item` и пишется в существующий `item.update`. `item_summary` и
  `item_detail` его отдают.

## 10. Вложения и ссылки (4в.3)

Решение — D-078. Два вида вложений:
* **сдача ученика** по ручному заданию с `answer_kind` `files` или `text_or_files` — файлы и ссылки рядом с текстом
  ответа (`answer.md`);
* **вложения преподавателя** к элементу ленты — файлы и ссылки к условию задания или к контест-элементу.

**Правила** — чистые функции [`classroom/attachment_rules.py`](../backend/app/classroom/attachment_rules.py) поверх
`access.py`. Требования чистоты те же, что в §6, плюс: модуль не читает файлы. Сервис передаёт ему:
* имя, размер и первые 8 КБ каждого файла (`HEAD_BYTES`, столько же читает `content_files`);
* числа и суммы, прочитанные под своими блокировками;
* `now`.

Таблица случаев — `tests/test_attachment_rules_units.py`.

### Имя

Сервис сначала обрезает имя до базового (`content_files.clean_name`). Затем `check_name`:

| Код | Когда |
|---|---|
| `file_name_invalid` | пусто, только точки или пробелы, пробел по краям, `/` или `\`, управляющий или форматный символ (NUL, перевод строки, знаки направления текста), одиночный суррогат, больше 150 символов (как `content_files.NAME_MAX`) |
| `file_type_not_allowed` | нет расширения (`README`, `notes.`, `.py`) или последнего расширения нет в белом списке |
| `file_empty` | файл в 0 байт — любого типа, текстовый тоже: пустой `.txt` закрыл бы требование `files_required`, ничего не сдав |

Кириллица допустима. Решает только **последнее** расширение, в нижнем регистре: `ПРОЕКТ.SB3` и `отчёт.v2.pdf`
проходят, `run.py.exe` — нет (`.exe` не в списке).

Повтор имени — `duplicate_name`. Сравнение без учёта регистра (`casefold`): на Windows `a.py` и `A.PY` при сохранении
затёрли бы друг друга. Повтор проверяется внутри одной сдачи, а у элемента — с его уже приложенными файлами. У ссылок
имён нет.

### Белый список и содержимое

| Расширения | Содержимое |
|---|---|
| `py c cpp h hpp txt md csv json ipynb` | не проверяется: исходник в cp1251 с Windows принимается; при отдаче (`FILES.md`) не-UTF-8 и так уходит двоичным вложением |
| `zip docx xlsx pptx odt ods odp sb3` | сигнатура zip `PK\x03\x04`; пустой zip (`PK\x05\x06`) — отказ |
| `pdf` | начинается с `%PDF-` |
| `png`, `jpg` / `jpeg`, `webp` | сигнатура PNG / JPEG / WebP, **совпадающая с расширением** |

Несовпадение даёт `file_content_mismatch`. Картинки при загрузке проверяются строже, чем при отдаче: D-070 отдаёт
`.jpg` с PNG внутри как `image/png`, а загрузка такой файл отклоняет, и ученик пересохраняет его сразу. SVG, HTML,
GIF, HEIC, исполняемые и всё прочее в список не входят. Сигнатуры совпадают с `content_files.sniff` и
`protocol/problem_package.picture_kind`, тест держит их в согласии.

Один файл (`check_file`) проверяется по порядку: имя → тип → пустой (`file_empty`) → размер (`file_too_large`) →
содержимое.

### Ссылка

Ссылка — это данные. Сервер её **никогда не открывает**: ни превью, ни проверки доступности, никаких запросов по URL
(защита от SSRF). `check_link` берёт URL без пробелов по краям; так он и хранится.

| Код | Когда |
|---|---|
| `link_invalid` | схема не `http` / `https` (регистр любой: `HTTPS://…` принимается); нет хоста (`https://`, `https:example.ru`, `//example.ru`); `user:pass@` в части хоста (`https://good.ru@evil.example`); `\`; пробел любого вида, управляющий или форматный символ внутри; порт не число; длиннее 2000 символов |
| `link_title_invalid` | заголовок (необязателен) длиннее 200 символов, с управляющими символами, одиночным суррогатом или форматными символами, кроме соединителя эмодзи (U+200D) |

`javascript:`, `data:`, `file:`, `ftp:` — `link_invalid`. Знак `@` в пути (`youtube.com/@channel`) допустим.
Нелатинский хост (`пример.рф`) хранится как прислан. Как показывать домен, решает модуль 5 (ROADMAP).

### Ответ: вид × текст × файлы × ссылки

Шаги 9–13 `can_submit_work` (§6). Файлы и ссылки для него — одно число.

| `answer_kind` | ничего | только текст | только файлы или ссылки | текст и файлы |
|---|---|---|---|---|
| `mark` | ok | `text_not_expected` | `files_not_expected` | `text_not_expected` |
| `text` | `answer_required` | ok | `answer_required` | `files_not_expected` |
| `files` | `files_required` | `text_not_expected` | ok | `text_not_expected` |
| `text_or_files` | `answer_required` | ok | ok | ok |

### Лимиты сдачи

`check_hand_in(files, links, limits)` проверяет по порядку, первая неудача даёт код:
1. `too_many_files` — файлов и ссылок вместе больше `JUDGE_SUBMISSION_FILES_MAX` (10); `answer.md` не считается;
2. каждый файл по порядку — `check_file` с пределом `JUDGE_SUBMISSION_FILE_MAX_MB` (20 МБ);
3. `duplicate_name`;
4. `submission_too_large` — сумма файлов больше `JUDGE_SUBMISSION_TOTAL_MAX_MB` (50 МБ);
5. каждая ссылка по порядку — `check_link`.

Ответ — `OK` или `Refusal(code, index)`: номер файла или ссылки, о которых отказ (`None` — о списке целиком).
Граница включительная: ровно предел проходит, на единицу больше — нет.

Полный порядок сдачи: `can_submit_work` (§6) → `check_hand_in` → `quota_ok`.

### Квота ученика

`quota_ok(used, adding, quota)`:
* `used` — сумма размеров **различных** блобов (distinct `sha256`) во всех сдачах ученика, вместе с `answer.md`;
* `adding` — размеры блобов новой сдачи, которых у ученика ещё нет.

Поэтому пересдача тех же файлов квоту не расходует, а история сдач её не съедает. Граница включительная.
* Сдача без новых блобов проходит всегда, даже если квоту уменьшили ниже `used`.
* `quota` — `JUDGE_STUDENT_QUOTA_MB` (200 МБ); пусто или 0 — без предела.
* Отказ — `quota_exceeded`; сообщение сервиса просит обратиться к преподавателю.

Ссылки в квоту не входят.

### Вложения преподавателя

`check_new_attachment(имена у элемента, их число, file= | link=)` — ещё одно вложение элемента. Отказы по порядку:
1. `too_many_attachments` — больше `JUDGE_ITEM_ATTACHMENTS_MAX` (20) файлов и ссылок у элемента;
2. коды `check_file` с пределом `JUDGE_ATTACHMENT_MAX_MB` (50 МБ);
3. `duplicate_name`;
4. коды ссылки.

Суммы на элемент нет.

`can_change_attachments(item)` — добавлять, удалять и переставлять можно в черновике и в опубликованном элементе;
архивный только читается (`item_archived`).

### Кто видит

`can_view_item_files` — вложения преподавателя входят в страницу элемента:
* у задания — `access.can_view_assignment`: условие и вложения скрываются вместе после срока при
  `after_due_statement = hidden`, в том числе у ученика, у которого уже есть работа;
* у контест-элемента — `access.item_listed`;
* черновик, архив, раньше `available_from`, не адресат — нет;
* у элемента-материала (4в.4) — `access.item_listed`, как у контест-элемента; файлы самого материала — §11;
* админы видят всё.

Свои файлы и ссылки сдачи ученик видит всегда, как свою работу (`access.can_see_own_work`).

### В базе

Схема (этап 2, D-079, `DATA_MODEL.md` «Изменения 4в.3»): файлы сдачи — `assignment_submission_files` с видом `text`
(`answer.md`) или `file`, ссылки сдачи — `assignment_submission_links`, вложения преподавателя — `attachments`. База
держит те же пределы мягче правил (имя до 150, URL до 2000 и `http(s)://`, заголовок до 200, файл не пустой, имена без
учёта регистра через `lower()`): правила отказывают раньше и с кодом, база не даёт сохранить заведомо неверное.

### Сервисы (этап 3, D-080)

**Приём файла** — `blobstore.Incoming` (`blobs.incoming(name, limit)`, в блоке `with`):
* тело пишется кусками во временный файл в `<корень блобов>/tmp` — на той же файловой системе, что блобы; sha256,
  размер и первые 8 КБ (`HEAD_BYTES`) считаются по ходу записи. Каталог `tmp` блобом не считается: блоб — это только
  `<корень>/<2 hex>/<64 hex>` (обязательство сборщика модуля 6);
* в хранилище файл попадает одним `os.replace` (`adopt`) — последним шагом сервиса, когда все проверки пройдены;
  такой блоб уже есть — копия удаляется;
* закрытие (`close`, выход из `with`) удаляет временный файл, если он не принят. Поэтому обрыв соединения, тело сверх
  лимита (413 от `http_body.save_body` или `TooLarge` самого `Incoming`) и отказ проверки (тип, имя, квота, правила
  сдачи) не оставляют ни блоба, ни временного файла. Закрывает тот, кто создал: API, judgectl, тест;
* остаётся одно окно: сбой базы после `adopt` оставит блоб без строки — его уберёт сборщик модуля 6.

Имя сначала приводится к базовому (`content_files.clean_name`: путь `C:\…\рисунок.PNG` даёт `рисунок.PNG`), затем
правила (`check_name` и далее).

**Вложения преподавателя** — `classroom/attachments.py`:
* `add_file`, `add_link`, `remove`, `reorder` берут строку элемента `FOR UPDATE` (`items.lock_item`) и читают
  вложения после неё. Два добавления сразу идут одно за другим: при 19 вложениях из двух параллельных ровно одно
  принято, второе — `too_many_attachments`; два файла с именами, различными только регистром, — `duplicate_name`;
* `can_change_attachments`: черновик и опубликованный меняются, архивный только читается (`item_archived`);
* `add_link`: URL и заголовок без пробелов по краям, пустой заголовок — нет заголовка;
* `remove`: удаляется строка, блоб остаётся; чужое вложение (другого элемента) — `attachment_not_found`;
* `reorder(ids)`: список должен **ровно** совпадать с текущим набором — без пропусков, лишних и повторов;
  иначе `attachment_order_invalid` (в `data` — `missing`, `extra`, `repeated`). Тот же порядок — без записи в аудит;
* аудит `item.attachment_add` / `item.attachment_remove` / `item.attachment_order` — **без содержимого**: у файла
  имя, sha256 и размер, у ссылки URL и заголовок, у порядка — `before` и `after`;
* удаление черновика (`items.delete_item`) уносит его вложения (`CASCADE`), блобы остаются.

**Кто видит** — `attachments.can_view` / `visible_attachments` / `item_file(viewer, item, id, now)`: админ — всё;
ученик — по `can_view_item_files` с входными данными `items.view_inputs` (адресат, продления, контест). Чего ученику
видеть нельзя, того «нет»: `visible_attachments` — `None`, `item_file` — `attachment_not_found`, как и для вложения
чужого элемента или ссылки. Файл отдаётся `content_files.file_response(…, request=request)` только после этой
проверки (`ADMIN_API.md` §5.10). До приёма тела загрузки админский API зовёт `precheck_file` — дешёвые отказы без
блокировки (архивный, лимит числа, тип по имени, повтор имени); `add_file` после тела решает всё заново под
блокировкой элемента.

**Сдача** — `works.submit_work(…, files=[Incoming], links=[LinkIn(url, title)], limits, quota)`:
1. `can_submit_work` с числом файлов и ссылок;
2. `check_hand_in` (имена, типы, пустые, размеры, повторы, сумма, ссылки; отказ с номером в `data.index`);
3. `pg_advisory_xact_lock(STUDENT_FILES, ученик)`, затем блокировка работы, `can_submit_work` ещё раз;
4. квота: `quota_used` — сумма размеров различных `sha256` во всех сдачах ученика; добавляется только то, чего у
   него ещё нет (текст ответа тоже). Отказ — `quota_exceeded` (409; сообщение просит обратиться к преподавателю,
   в `data` — `used`, `adding`, `quota`);
5. только теперь блобы принимаются в хранилище; строки: текст — `text`, позиция 0; файлы — `file`, позиции 1…;
   ссылки — своя таблица.

Блокировка ученика берётся при каждой сдаче (текст тоже идёт в квоту), всегда **до** блокировки работы — один
порядок для всех, без взаимных блокировок. Две сдачи одного ученика на разные элементы сразу не выходят за квоту;
одна и та же сдача 10 раз расходует квоту один раз.

**Файл работы** — `works.work_file(viewer, item, student, file_id)`: файл ищется по паре (элемент, ученик) и id —
текст ответа тоже. Админ видит любую работу, ученик — только свою (`can_see_own_work`). Файл чужой работы, другого
элемента или чужой пары — `file_not_found`. Карточка работы (`work_detail`) у каждой сдачи перечисляет `files`
(`id`, `kind`, `name`, `size`, `sha256`) и `links` (`id`, `url`, `title`) — без содержимого. `answer_text` берёт
текст по виду `text`, а не по имени: файл ученика `answer.md` им не является.

**Лимиты** — `Settings.files` (`FileSettings`), env `JUDGE_SUBMISSION_FILES_MAX`, `JUDGE_SUBMISSION_FILE_MAX_MB`,
`JUDGE_SUBMISSION_TOTAL_MAX_MB`, `JUDGE_STUDENT_QUOTA_MB` (0 — без квоты), `JUDGE_ITEM_ATTACHMENTS_MAX`,
`JUDGE_ATTACHMENT_MAX_MB` (пример — `deploy/env/backend.env.example`); неверное значение останавливает запуск.
`attachments.hand_in_limits` / `teacher_limits` превращают их в `Limits` правил.

judgectl и админский API — этапы 4 и 5. Коды сервисов `file_not_found` (404) и `quota_exceeded` (409, только сдача
ученика) уже в `STATUS`; маршрута к `file_not_found` до этапа 5 нет (`NO_ROUTE_YET`). Коды `attachment_rules` войдут
в `STATUS` на этапе 5.

## 11. Библиотека материалов (4в.4)

Решение — D-083. Материал — самостоятельная сущность библиотеки: памятка, справка, конспект. Ученику он выдаётся
тремя путями: через Справочник, через элемент ленты `material` и по ссылке `[[памятка:slug]]` из условия задачи или
текста элемента. Схема — `DATA_MODEL.md` «Изменения 4в.4» (D-084), сервисы — этап 3, judgectl (`material`, `section`,
`item create --kind material`; `JUDGECTL.md`, D-086) и админский API (`ADMIN_API.md` §5.11, D-087) — этапы 4 и 5
сессии 4в.4; эндпоинты ученика — 4б.2, отрисовка — модуль 5.

**Чистые функции** — [`materials/links.py`](../backend/app/materials/links.py) (грамматика ссылок) и
[`materials/rules.py`](../backend/app/materials/rules.py) (ввод и доступ). Требования чистоты — как в §6: без базы и
своих часов, даты сравнивают только `deadline_rules` через `classroom/access.py` и `contests/access.py`. Таблица
случаев — `tests/test_material_rules_units.py`.

### Материал и версии

* **slug** — как у задачи: `[a-z0-9][a-z0-9-]{1,62}` (`slug_invalid`). Сервис не обрезает и не переводит регистр.
  **После создания slug не меняется** (`slug_immutable`): ссылки в неизменяемых версиях задач нельзя исправить,
  переименование сломало бы их молча. Вместо переименования — новый материал, а старый в архив.
* **Название** — 1…200 символов после схлопывания пробелов, без управляющих и форматных символов (`title_invalid`).
  Правится на месте, в версию не входит.
* **Версии неизменяемы.** Каждое изменение содержимого — новая версия: текст, добавление и удаление файла или
  ссылки, порядок вложений. Вложения принадлежат версии; новая версия копирует строки, блобы общие. Ученики и ссылки
  всегда видят **последнюю** версию, преподаватель — всю историю. Закрепления версии нет: памятки исправляют, и
  исправление должно дойти до всех.
* **Текст** — Markdown, хранится как прислан (недоверенный: в модуле 5 только через санитайзер). Может быть пустым
  (материал из одних вложений). `body_invalid` — NUL или одиночный суррогат; `body_too_long` — больше 100 000 символов.
* **Архив вместо удаления.** Архивный материал пропадает из Справочника, но открывается по остальным основаниям (лента,
  ссылки).

### Ссылки `[[памятка:slug]]`

| Запись | Что видит читатель |
|---|---|
| `[[памятка:slug]]` | название материала |
| `[[памятка:slug\|текст]]` | `текст` (1…200 символов после обрезки, без перевода строки, `[`, `]`, `\|`, управляющих и форматных символов) |

* Префикс — слово «памятка» в любом регистре и двоеточие, без пробелов внутри скобок. `[[memo:…]]` — просто текст.
* Грамматика одна — регулярное выражение, не разбор Markdown. Поэтому ссылка внутри кода (бэктики, блоки) — тоже
  ссылка: сервер и интерфейс модуля 5 не могут разойтись в том, где ссылка. Экранирования нет.
* Похожее на ссылку, но неверное (`[[памятка:Bad Slug]]`, `[[ памятка:x]]`, пустой текст) — **не ссылка**. Текст
  хранится как есть, преподаватель получает предупреждение.
* **Неизвестный slug — предупреждение, не отказ** — везде: при импорте задачи, в тексте элемента ленты, в тексте
  материала. Ссылка разрешается при чтении, поэтому материал, созданный позже, «оживляет» её. Архивный материал —
  тоже предупреждение.
* `references:` в `problem.yaml` нет: ссылки задачи берутся из текста её условий.

**Разрешение для отрисовки** — `rules.resolve`, одна запись на каждый slug текста. Ученик получает `{slug, available}`,
а `id` и `title` — только у доступного материала. «Нет такого», «архивный без оснований» и «нет доступа» для ученика
выглядят одинаково: ни существование, ни название не утекают. Админ получает статус: `ok`, `archived` или `unknown`.

### Кто открывает материал

Админ — любой. Ученик — последнюю версию, если есть хотя бы одно основание (`rules.open_basis` называет первое):

| # | Основание | Когда |
|---|---|---|
| 1 | `library` | Справочник: материал не в архиве, аудитория библиотеки `all_students` или неархивная группа, в которой ученик **сейчас** (`in_library`) |
| 2 | `feed` | элемент `material` этого материала в ленте ученика (`access.item_listed`: опубликован, адресован, наступил `available_from`, не в архиве) |
| 3 | `item_link` | элемент, текст которого ссылается на материал, в ленте ученика (`item_listed`). Срок и скрытое после срока условие доступ **не отменяют** |
| 4 | `problem_link` | задача контеста, условие закреплённой версии которой ссылается на материал, видна ученику: `contests.access.problem_visible` (`CONTESTS.md` §4). **Участие не нужно**: ученику группы контеста в режиме `groups` памятка открыта ещё до входа. Окно, срок и скрытие условия не важны |

* Основания 2–4 действуют и для архивного материала.
* Ссылка из **другого материала** доступа не даёт: цепочек оснований нет. Такая ссылка у ученика без своего
  основания — «недоступна».
* Убранный из группы и ученик архивной группы теряют основания через группу (как в §2); ссылки из задач контеста —
  по правилам контеста.

### Справочник

Аудитория библиотеки у материала — `none` (по умолчанию), `all_students` или `groups` (группы — отдельные строки);
неверное значение — `library_invalid`. Разделы-темы — **не больше двух уровней**: раздел и подраздел (`section_too_deep`:
под подраздел или раздел с подразделами под другой; `section_invalid` — под самого себя). Материал может лежать в
нескольких разделах и на обоих уровнях; порядок разделов и материалов в разделе задаёт преподаватель — новый порядок
должен ровно совпадать с текущим набором (`order_invalid`, в данных — `missing`, `extra`, `repeated`). Название
раздела — как у материала (`section_title_invalid`). Поиск — по названию, без учёта регистра (этап 3). Тегов нет. Темы
ленты класса отложены.

### Элемент ленты `material`

Выкладка материала группам и ученикам: адресаты и отложенная публикация — как у остальных элементов, срока, сдачи и
оценки нет. Общая ветка комментариев — как у задания (`comments_enabled`), без личных веток. Вложения элемента
видны по `access.item_listed`, как у контест-элемента.

### Сервисы (этап 3, D-085)

[`materials/service.py`](../backend/app/materials/service.py) (материалы, версии, вложения, доступ),
[`materials/library.py`](../backend/app/materials/library.py) (Справочник),
[`materials/refs.py`](../backend/app/materials/refs.py) (ссылки при сохранении текста). Общие правила §7: `flush` без
`commit`, отказ — `FeedError` с кодом, действия преподавателя — в аудит **без содержимого** (длина текста, имя, sha256
и размер файла, URL и заголовок ссылки). Тесты — `tests/pg/test_materials_pg.py`.

**Материал.**
* `create_material(slug, title, body_md, library)` — материал и версия 1. Отказы: `slug_invalid`, `slug_taken` (и у
  архивного; два создания сразу — второе получает `slug_taken` от уникального индекса), `title_invalid`,
  `body_invalid`, `body_too_long`, `library_invalid`. Аудит `material.create`.
* `update_material(title=…, library=…)` — правка на месте; аудит `material.update` с `changes`. Ключ `slug`, отличный
  от текущего, — **`slug_immutable`**, ничего не меняется; тот же slug допустим. Прочие поля — `material_invalid`.
* `archive` / `unarchive` — `True`, если изменилось. Архивный материал только читается: правки, вложения, группы
  Справочника, место в разделе, новый элемент ленты — `material_archived`.
* `set_library_groups` / `add_library_groups` / `remove_library_groups` — группы Справочника; новая группа не
  архивная (`group_archived`); аудит `material.library_groups` (`before`, `after`).

**Версии.** Все изменения содержимого идут под блокировкой строки материала (`FOR UPDATE`), поэтому две правки сразу
дают две версии подряд, без пропусков и повторов номера, и вторая строится поверх первой (тест на двух соединениях).
* `new_version(body_md)` — новый текст: версия + 1 с вложениями последней. Тот же текст — версии нет (`created`
  ложно). Аудит `material.version` (`version`, `from`, `body_chars`).
* Вложения версии — правила и лимиты 4в.3 (`attachment_rules`, `teacher_limits`, `JUDGE_ITEM_ATTACHMENTS_MAX`,
  `JUDGE_ATTACHMENT_MAX_MB`):
  - `precheck_file(name)` — до тела, без блокировки и записи: архивный, лимит числа, тип по имени, повтор имени;
  - `add_file(upload)` — после тела решает всё заново под блокировкой материала (архив, лимит, имя, пустой, размер,
    содержимое); блоб принимается в хранилище последним шагом, отказ не оставляет ни блоба, ни файла в `tmp`;
  - `add_link`, `remove(id)`, `reorder(ids)` (`attachment_order_invalid` с `missing` / `extra` / `repeated`; тот же
    порядок — версии нет);
  - каждое изменение — новая версия: строки вложений копируются (новые id, блобы общие), прежние версии не
    меняются. Id вложений — у последней версии; удалить или переставить вложение старой версии нельзя
    (`attachment_not_found`). Аудит `material.attachment_add` / `_remove` / `_order` с номером версии.
* `versions(material)` — история без текстов (длина, число вложений); `version_detail(material, n)` — одна версия для
  админа (`version_not_found`).

**Доступ.** `open_inputs` собирает для `rules.open_basis` всё из базы: группы Справочника и текущие группы ученика;
опубликованные элементы `material` этого материала и опубликованные элементы, текст которых на него ссылается
(`material_refs`), с тем, что нужно `item_listed` (`items.view_inputs`); задачи контестов, чья закреплённая версия
ссылается на slug, с участием и признаком группы контеста (`contests.access_inputs`).
* `material_view(viewer, material)` — последняя версия: текст как хранится, вложения (без содержимого), ссылки текста,
  разрешённые для читателя (`resolve`). Ученику без основания — `material_not_found`, по любой причине. Админ
  получает ещё slug, аудиторию, группы, разделы, число версий.
* `material_file(viewer, material, id, version=None)` — файл для `content_files.file_response` после проверки. Ученик:
  только последняя версия и только с основанием (`material_not_found`); номер версии от ученика не принимается. Админ:
  любая версия. Ссылка, вложение другой версии, нет такого — `attachment_not_found`.
* `resolve(viewer, texts)` — ссылки текстов, по одной на slug: ученику «нет такого», «архивный без оснований» и «нет
  доступа» дают один и тот же ответ `{slug, available: false}` (тест сравнивает ответы целиком).
* `where_used(material)` — элементы `material` этого материала, элементы со ссылкой, версии задач (`slug@v`),
  материалы, **последняя** версия которых ссылается на него.

**Ссылки при сохранении** (`refs.replace`, `refs.warnings`): строки `material_refs` источника пишутся заново при каждом
сохранении его текста — версия задачи (все условия, при импорте), элемент ленты (`create_item`, `update_item` при
смене `body_md`), версия материала. Предупреждения (неверная запись, нет такого материала, архивный) — никогда не
отказ:
* `import_package` добавляет их к `warnings` результата — и в `created`, и в `exists`, и в `dry_run` (`new`), ключ —
  путь условия (`statement/ru.md: …`); строки `material_refs` пишутся **только** у созданной версии;
* элемент ленты — `items.link_warnings(item)`, в `item_detail` — поле `link_warnings`;
* материал — `warnings` результата `create_material` / `new_version`.

Неизвестный slug «оживает»: ссылка хранится по slug, и материал, созданный позже, сразу открывается по ней (тест).

**Справочник** (`library.py`). Изменения разделов и материалов в них идут по одной под advisory-блокировкой
`locks.LIBRARY`.
* `create_section(title, parent=None)` — в конец уровня; `rename_section`; `move_section(parent)` — в конец нового
  уровня (`section_too_deep`, `section_invalid`); `delete_section` — только без подразделов (`section_not_empty`),
  материалы лишь покидают раздел, в аудите — их slug.
* `place(material, section)` — в конец раздела (архивный — `material_archived`; уже там — `False`); `unplace`.
* `reorder_sections(ids, parent=None)`, `reorder_materials(section, ids)` — ровно текущий набор, иначе
  `order_invalid` (`missing`, `extra`, `repeated`).
* `library_view(viewer, now, q=None)` — разделы по порядку с материалами и подразделами плюс `unsorted` (материалы
  Справочника вне разделов). Ученик видит только материалы по `rules.in_library`, пустые для него разделы опущены;
  админ — всё, архивные с пометкой. С `q` — только поиск: `{query, materials}`.
* `search(viewer, q)` — `ILIKE` по названию без учёта регистра, кириллица тоже («циклы» находит «Циклы» и «ЦИКЛЫ»: базы
  в `C.UTF-8`); `%`, `_` и `\` ищутся буквально (экранирование, `ESCAPE '\'`).

**Элемент `material`** (`items.create_item(kind="material", material=…)`): без материала — `material_required`,
архивный — `material_archived`, материал у другого вида — `item_invalid`; пустое название — название материала.
Админский `POST /items` принимает `material` (slug) уже на этом этапе: иначе новые коды элемента не достигались бы
запросом (тест D-063). Остальные коды сервисов материалов войдут в `STATUS` на этапе 5.
