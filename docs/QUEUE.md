# Очередь проверки (модуль 3)

Очередь это таблица `judgements`: строка со статусом `queued` ждёт воркера. Отдельного брокера нет, только PostgreSQL.
Код: `backend/app/queue.py` (логика), `backend/app/loadinfo.py` (чистые функции: порядок и оценка ожидания).

## Жизненный цикл

```
enqueue ─▶ queued ─claim─▶ compiling ─heartbeat(phase=running)─▶ running ─result─▶ finished
              ▲                 │                                    │
              └── reaper / release / IE-retry ◀─────────────────────┘      (после max_attempts: internal_error)
```

* `attempt` растёт при каждой выдаче и служит **fencing-токеном**: результат принимается только от того воркера и с тем
  номером попытки, которые держат строку сейчас. Воркер, которого сочли мёртвым, а он очнулся, получит 409 и ничего не испортит.
* `failures` считает неудачные попытки (потерян воркер, внутренняя ошибка). Лимит `JUDGE_MAX_ATTEMPTS` (3) защищает от
  «ядовитой» посылки, которая валит воркер: после трёх провалов она заканчивается как `internal_error` (вердикт IE), а не
  крутится вечно. Штатная отдача задания при остановке воркера (`release`) провалом не считается.
* Инвариант в БД: у посылки не больше одного незавершённого judgement (`uq_judgements_active`) и не больше одного текущего (`uq_judgements_current`).

## Выдача: справедливость

Порядок выдачи (SQL в `CLAIM_SQL`, эталон на Python `loadinfo.fair_key`, их совпадение проверяет `tests/pg`):

1. `priority` (меньше раньше): свежие посылки 0, перепроверки 10, срочное можно сделать отрицательным;
2. сколько проверок **этого ученика** идёт прямо сейчас (меньше раньше): один ученик не займёт все воркеры;
3. сколько проверок ученика **стартовало за последние 5 минут** (`JUDGE_FAIR_WINDOW_S`): кто сыплет посылки, уступает тем, кто давно молчит;
4. возраст (`created_at`, `id`).

Это не жёсткий лимит: если в очереди один ученик, он получает все воркеры (работа не простаивает).

Claim выполняется под `pg_advisory_xact_lock`. Без него два одновременных claim считали бы справедливость по одному
снимку и оба взяли бы посылки одного ученика. Блокировка живёт миллисекунды, воркеров 5-6, это не узкое место.
`FOR UPDATE SKIP LOCKED` оставлен как страховка: claim никогда не ждёт строку, которую держит другой писатель
(отмена, перепроверка). Если когда-нибудь воркеров станет десятки, блокировку можно убрать ценой небольшого отклонения от справедливости.

## Зависшие задания

* Воркер шлёт heartbeat раз в 5 с (заодно прогресс «проверено 7 из 20»). Нет heartbeat 30 с (`JUDGE_HEARTBEAT_TIMEOUT_S`) →
  reaper (`python -m app.maintenance`, свой systemd-юнит) возвращает задание в очередь.
* Задание, которое идёт дольше `JUDGE_MAX_JUDGING_S` (30 мин), отбирается даже у «живого» воркера; воркер сам тоже не
  работает дольше `JUDGE_JOB_DEADLINE_S`.
* Воркер, перезапущенный под тем же именем, при регистрации сразу возвращает то, что держал прошлый экземпляр
  (иначе задание ждало бы таймаут). Новая регистрация меняет `instance_id`: старый процесс с тем же именем получит 409 `superseded` и остановится.
* Heartbeat отвечает `cancel: true`, если задание отобрано: воркер прекращает впустую жечь CPU (отмена проверяется между тестами).

## Перепроверка без потери истории

`request_rejudge` создаёт **новый** judgement (`reason=rejudge`, `is_current=false`, приоритет 10); старый со всеми `test_results` остаётся.
Пока перепроверка ждёт или идёт, ученик видит старый вердикт. Когда она завершится без внутренней ошибки, флаг `is_current` переходит к ней.
Если перепроверка закончилась IE, хороший старый вердикт не заменяется. Если у посылки уже есть задание в очереди, оно
не дублируется, а перенацеливается на актуальную версию задачи (`retargeted`); если оно уже выполняется, ответ `already_running`.
`rejudge_contest_problem` делает это для всех посылок задачи контеста (можно фильтровать по текущим вердиктам).
`judgements.problem_version_id` хранит, по какой версии задачи проверяли.

## Загрузка для учеников

`load_snapshot()` возвращает: длину очереди, воркеры онлайн/заняты, типичное время проверки (медиана за час),
уровень (`free` / `busy` / `overloaded` / `offline`) и для конкретного ученика место в очереди и оценку ожидания.
Место считается в том же справедливом порядке (по снимку, без учёта будущих изменений), оценка в `loadinfo.estimate_wait_seconds`.
Это приближение: «около N секунд», а не обещание. Публичный эндпоинт появится в модуле 4, он просто отдаст `snapshot.to_dict()`.

| Протокол воркер-бэкенд, fencing, release, потеря lease, вытеснение, воркер целиком | `tests/test_worker_e2e.py` против модели бэкенда в памяти, **запущены** |
| SQL очереди, индексы, `models.py` на реальном SQLAlchemy/PostgreSQL | `tests/pg/test_queue_pg.py`, **НЕ запускались** (нет PostgreSQL) |
| FastAPI-слой | `tests/pg/test_worker_api_pg.py`, **НЕ запускался** |

Запуск у вас:

```bash
createdb judge_test            # или через psql
export JUDGE_TEST_DATABASE_URL=postgresql+psycopg://USER:PASS@127.0.0.1:5432/judge_test
pip install -r requirements.txt
python -m unittest discover -s tests/pg -t . -v
```

Каждый тест работает в собственной временной схеме и удаляет её. Первый запуск заодно впервые исполнит `models.py`.
