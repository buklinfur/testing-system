# Импорт задач

Единственный путь создать версию задачи (Р26): пакет → безопасная распаковка → проверка формата → канонический
список файлов → блобы и `ProblemVersion`. Формат пакета — [`PROBLEM_FORMAT.md`](PROBLEM_FORMAT.md); решения —
Р26–Р31 и §5.6 в [`MODULE_4A.md`](MODULE_4A.md).

| Где | Что |
|---|---|
| [`protocol/problem_package.py`](../protocol/problem_package.py) | проверка пакета (схема + семантика), маски тестов, мусор, `content_sha256`; общий для бэкенда и инструментов, без импорта раннера |
| [`protocol/schemas/problem.schema.json`](../protocol/schemas/problem.schema.json) | JSON Schema для `problem.yaml` (лежит в `protocol/`, потому что на установку копируется только код) |
| [`backend/app/problems/unpack.py`](../backend/app/problems/unpack.py) | безопасная распаковка zip и те же проверки для папки |
| [`backend/app/problems/importer.py`](../backend/app/problems/importer.py) | `import_package`: дедупликация, версии, блобы, аудит |
| [`tools/validate_problem.py`](../tools/validate_problem.py) | те же проверки из командной строки (для автора задачи) |
| [`tools/pack-problem.sh`](../tools/pack-problem.sh) | zip папки задачи в stdout с тем же фильтром мусора |
| [`tools/make-bad-archives.py`](../tools/make-bad-archives.py) | вредоносные архивы для ручной проверки импорта |

Импорт из консоли — `judgectl problem import` ([`JUDGECTL.md`](JUDGECTL.md)): папка, zip или zip на stdin, `--dry-run`
проверяет всё и ничего не пишет. `dev_seed` импортирует тем же путём. `import_package` принимает **файл** архива, а не
байты: stdin judgectl и тело запроса админского API пишутся во временный файл потоком со счётчиком, блобы копируются
кусками — архив целиком в память не читается.

## 1. Безопасная распаковка (Р27)

Своя, не `ZipFile.extractall`. **До записи первого байта** проверяются все имена архива; любое нарушение — отказ
со списком **всех** нарушений:

* абсолютные пути (`/…`, `C:…`), обратные слэши, `..`, пустые части и `.` в имени;
* символические ссылки и спецфайлы (каналы, устройства, сокеты) — по типу файла Unix в `external_attr`;
* повторяющиеся имена;
* методы сжатия кроме **stored** и **deflate** (bzip2, lzma, deflate64) и зашифрованные записи: чем меньше
  распаковщиков видит недоверенные данные, тем лучше, а обычные архиваторы (Windows, Excel, `zip`, `pack-problem.sh`)
  пишут deflate;
* больше `JUDGE_IMPORT_MAX_FILES` (5000) записей;
* архив больше `JUDGE_IMPORT_MAX_ARCHIVE_MB` (100 МБ);
* сумма размеров, **заявленных** в заголовках, больше `JUDGE_IMPORT_MAX_UNPACKED_MB` (512 МБ) — ранний дешёвый отказ:
  бомба не успевает записать ни байта.

**Главная защита от zip-бомб — лимит распакованного объёма и потоковый счётчик.** Файлы распаковываются потоком,
байты считаются по факту, **заявленным размерам не доверяем в сторону уменьшения**: распаковано больше 512 МБ —
отказ. Если заголовок занижает размер, `zipfile` останавливается на заявленном и сообщает о несовпадении CRC — тоже
отказ; счётчик остаётся вторым рубежом на случай иного поведения `zipfile`.

Проверка коэффициента сжатия (`JUDGE_IMPORT_MAX_RATIO`, на файл и в сумме) **по умолчанию выключена** (`0`).
У deflate потолок около 1030, а законные однообразные тесты в него упираются: миллион однозначных чисел (`7 7 7 …`)
сжимается примерно в 1020 раз, миллион чисел `1000000000` — примерно в 515 (оба импортируются, есть тесты). Порог
отличал бы бомбу от теста хуже, чем лимит объёма, поэтому защита — объём; настройку можно включить, если нужно.

Файлы создаются с `O_EXCL | O_NOFOLLOW` во временной папке импорта, которая удаляется после него. Если все файлы
лежат в одной верхней папке (заархивирована папка задачи), эта папка снимается.

Импорт **папки** проходит те же проверки: симлинки и спецфайлы — ошибка, лимиты числа файлов и общего размера.

Лимиты задаются в `/etc/judge/backend.env` (см. `deploy/env/backend.env.example`).

## 2. Мусор

Не входит в хеш, не сохраняется и не считается второй верхней папкой: `.DS_Store`, `Thumbs.db`, `desktop.ini`,
`*:Zone.Identifier`, `__MACOSX/`, `.git/`, `__pycache__/`, `*.pyc`, `*~`.

## 3. Проверка пакета (Р28)

* `problem.yaml` по JSON Schema. **`jsonschema` обязательна:** без неё проверка — ошибка, а не пропуск
  (`tools/validate_problem.py` раньше только предупреждал).
* Семантика: файлы условий, чекера, интерактора, валидатора и эталонов существуют; языки программ жюри известны
  системе (`protocol/languages.py`), язык эталона определяется по расширению; у каждого `.in` есть `.out`, если
  чекер его требует; тест не входит в две группы; в группе нет двух тестов с одним именем из разных папок;
  зависимости групп существуют и без циклов; вопросы `choice` и ответы `text_answer` согласованы; `wall_ms ≥ time_ms`.
* **Маски тестов** сопоставляются со списком файлов пакета, а не с файловой системой: маска физически не может
  выйти за пределы пакета или пройти по ссылке. `..`, абсолютные пути и обратные слэши в масках — ошибка.
  Синтаксис как у `Path.glob`: `*`, `?`, `[…]`, `**/`.
* Условия — текст UTF-8.

Все ошибки выдаются разом. Пока пакет не прошёл все проверки, в БД и в хранилище блобов ничего не пишется.

## 4. Версии и идентичность (Р29, Р30)

* Задача определяется по `slug` из `problem.yaml`; новой задачи нет — она создаётся.
* **`content_sha256`** = sha256 от отсортированных строк «путь `\0` sha256 файла» всех файлов пакета без мусора.
  Совпал с версией этой задачи — ничего не пишется, результат «уже есть как vN». Иначе — версия N+1. Меняется хоть
  байт условия, картинки или эталона — новая версия; порядок файлов в архиве и мусор роли не играют, папка и её zip
  дают одну версию.
* Сохраняются: каждый файл пакета блобом и список `files` (`{путь: sha256}`), условия (текст по языкам), группы и
  тесты, проверка (`checker`), интерактор, валидатор и эталонные решения (`programs.role = solution` с ожидаемым
  вердиктом — для проверки воркером в 4а.4), нормализованный `config` (`problem.yaml` без `test_groups` и `solutions`,
  его получает воркер), `manifest_sha256`, исходный zip (`package_sha256`, если импорт из архива).
* Статус новой версии — `ready` (проверки воркером пока нет; в 4а.4 станет `pending_check`).
* Версии неизменяемы: импорт никогда не меняет существующую.
* Архивная задача (`problems.archived`) импорт отвергает с подсказкой `judgectl problem unarchive`.
* Импорты одной задачи выполняются по очереди (`pg_advisory_xact_lock` по `slug`): номера версий и «уже есть»
  остаются верными при одновременных импортах.
* Аудит `problem.import` (slug, версия, `content_sha256`, число файлов, источник). Повтор («уже есть») ничего не пишет.
* Владелец задачи (`problems.owner_id`) — пользователь веба, если импорт из веба (4а.3); при импорте из консоли — пусто
  (миграция `9e2f4a7c1b30`). `dev_seed` указывает `dev-teacher`.

## 5. Известные ограничения

* Блобы пишутся до фиксации транзакции: если после записи блобов сломается БД, на диске останутся блобы без ссылок.
  Их число покажет `judgectl status` (этап 5), сборщик — модуль 6.
* Проверка версии воркером (компиляция проверки, прогон эталонов) — сессия 4а.4.

## 6. Ручная проверка

```bash
python tools/validate_problem.py problems-examples/sum-of-two
tools/pack-problem.sh problems-examples/sum-of-two > /tmp/sum.zip      # тот же набор файлов, что берёт импорт
python3 tools/make-bad-archives.py /tmp/bad                            # 11 архивов, каждый должен быть отвергнут
                                                                       # (бомба — 600 МБ нулей: по объёму;
                                                                       #  bzip2.zip и lzma.zip — по методу сжатия)
```
