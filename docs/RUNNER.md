# Раннер: компиляция, запуск в песочнице, вердикты

Раннер (`runner/`) не знает ни про базу данных, ни про веб. Он получает пакет задачи и решение, а возвращает отчёт. Очередь, воркеры и API появятся в модулях 3 и 4 и будут вызывать `Judge.judge_submission(...)`.

## Состав

| Модуль | Назначение |
|---|---|
| `sandbox/isolate.py` | **Боевой** бэкенд поверх `isolate` (cgroup v2): лимиты, запрет сети, урезанная файловая система |
| `sandbox/local.py` | **Небезопасный** бэкенд для разработки и тестов (rlimits, обычный процесс). Включается только `JUDGE_ALLOW_UNSAFE_LOCAL=1` |
| `languages.py` | Профили Python, C, C++: команды сборки и запуска |
| `archive.py` | Распаковка zip: защита от zip-slip, символических ссылок, бомб, шифрования |
| `compile.py` | Сборка (или проверка синтаксиса Python) в песочнице, очистка лога от путей сервера |
| `package.py` | Загрузка пакета задачи (`problem.yaml` и файлы тестов) |
| `checkers.py` | Встроенные чекеры `exact`, `tokens`, `float` |
| `judge.py` | Оркестрация: группы, зависимости, ранняя остановка, чекеры, интерактор, баллы |
| `scoring.py` | Подсчёт баллов и итогового вердикта (чистые функции) |
| `explain.py` | Расшифровки вердиктов и **вид для ученика** (`student_view`) |
| `quiz.py` | Проверка задач без кода (`choice`, `text_answer`) |
| `redteam.py`, `selftest.py` | Вредные программы и проверка допущений песочницы |
| `cli.py` | Командная строка |

## Как устроена проверка

1. Исходники (файл или zip) распаковываются с проверками, дальше сборка в отдельной песочнице с лимитами на сборку. Для Python делается проверка синтаксиса, и ошибка тоже становится `CE`.
2. Для **каждого теста** создаётся новая песочница: туда кладётся исполняемый файл и вход, программа запускается с лимитами, вывод читается через канал с ограничением размера. Состояние одного теста не доходит до другого.
3. Ответ проверяется: встроенным чекером в процессе судьи (простой код над недоверенным текстом) или собственным чекером **в отдельной песочнице**.
4. Группы идут по порядку. Если зависимость не пройдена полностью, тесты группы получают `SKIPPED`. В `all_or_nothing` после первого провала остальные тесты тоже `SKIPPED` (флаг `run_all_tests` отключает это).
5. Интерактивные задачи: решение и интерактор работают в **двух разных песочницах**, а их stdin и stdout соединены каналами. Файлов жюри решению не видно. Если интерактор завершился с ошибкой раньше решения, виновен он (вердикт WA/PE), если решение упало раньше, то RE. Решение с TL, ML или OL всегда получает этот вердикт.
6. Любая внутренняя поломка (не компилируется чекер, интерактор вернул код 3, песочница отказала) даёт `IE`, а не ошибочный вердикт ученику.

## Лимиты

Итоговый лимит времени = лимит задачи × множитель языка × `per_language` задачи, но не выше системного потолка (`RunnerConfig`). Если лимит в задаче не указан, действует потолок. Wall-time = 2 × время + 1 с (страховка от зависаний). Время считается как CPU-время. Системные потолки по умолчанию: 10 с, 1024 МБ, 64 МБ вывода, 16 процессов.

## Запуск

```bash
pip install -r requirements.txt

# логика и тесты, без isolate (dev-бэкенд, НЕБЕЗОПАСНО для чужого кода)
export JUDGE_ALLOW_UNSAFE_LOCAL=1
python -m unittest discover -s tests -t .
python -m runner.cli --backend local selfcheck problems-examples/sum-of-two

# боевой режим в WSL2 (нужен isolate из модуля 0)
python -m runner.cli sandbox-check               # допущения о поведении isolate
python -m runner.cli redteam                     # вредные программы
python -m runner.cli selfcheck problems-examples/guess-number
python -m runner.cli judge problems-examples/sum-of-two my_solution.cpp
python -m runner.cli judge problems-examples/sum-of-two project.zip --lang cpp --archive
```

Два воркера на одной машине должны использовать разные `--box-base` (воркер занимает два номера: решение и чекер/интерактор). В конфигурации `isolate` должно хватать `num_boxes`.

## Что проверено, а что нет

Проверено автотестами (60 штук, dev-бэкенд): подсчёт баллов, зависимости групп, ранняя остановка, чекеры (включая собственный, PE), режим файлов, CE и санитизация лога, многофайловые архивы, злые архивы, интерактив (успех, WA, падение, взаимная блокировка без flush, выход без ответа), вид для ученика (скрытые тесты не раскрываются), задачи без кода, разбор мета-файла `isolate` на синтетических данных.

**Не проверено: сам `isolate`-бэкенд.** В среде, где писался код, нет `isolate`. Классификатор вердиктов по мета-файлу покрыт тестами, но реальный запуск нет. Первым делом на вашей машине:

1. `python -m runner.cli sandbox-check`: пять проверок допущений.
2. `python -m runner.cli redteam`: в конце должны быть только `ok`.
3. `python -m runner.cli selfcheck` на всех трёх задачах с кодом.

Допущения, на которые опирается бэкенд, и где искать причину, если проверка упадёт:

| Допущение | Если нарушено |
|---|---|
| stdin/stdout запускаемой программы наследуются от процесса `isolate` | падает проверка «two boxes talk through pipes»; интерактив придётся переделать на FIFO внутри песочницы |
| Файлы, положенные в `box` нами, читаются и запускаются внутри песочницы | `sandbox-check` падает на первом пункте; смотрите права на каталог `box` |
| Файл, созданный в `box` компилятором, читается нами | `IE` с текстом про права при чтении исполняемого файла |
| Опции `--cg-mem`, `--processes`, `--fsize`, `--stack`, `--extra-time`, `--silent`, `--meta`, `--env` приняты вашей версией | `IE` с текстом ошибки `isolate` |
| `status:TO/SG/RE/XX` и `cg-oom-killed` в мета-файле | вердикты ML и TL окажутся RE |

## Известные ограничения

- Тип `output_only` не реализован (будет ошибка `NotImplementedError`).
- Скомпилированные чекеры и интеракторы кэшируются только в памяти процесса. В модуле воркеров нужен дисковый кэш по хешу исходника.
- Решения компилируются заново для каждой посылки (кэш не нужен, посылки разные).
- Встроенные чекеры работают в процессе судьи. Для очень больших выводов это память процесса (но размер вывода ограничен потолком).
- Python-решения не ограничены по числу потоков отдельно от процессов (общий лимит 16).
- Частичные баллы от чекера (`min`) пока ведут себя как `all_or_nothing`.
- Python 3.10 и новее. Тесты прогонялись на 3.12.

## Наблюдение для методички

Встроенная функция `input()` в Python сама сбрасывает буфер вывода, поэтому Python-решения интерактивных задач почти не страдают от забытого `flush`. В C++ без `endl` или `cout.flush()` решение зависнет и получит `TL`. Это стоит сказать ученикам заранее: условие интерактивной задачи уже напоминает об этом.

## Дополнения модуля 3 (поведение прежнее, добавлены точки расширения)

* `Judge(config, factory=None, jury_cache=None)`: кэш скомпилированных чекеров/интеракторов подключаемый (`runner/jurycache.py`).
  Ключ зависит от содержимого исходника, языка, команды компиляции и `RunnerConfig.toolchain_id`. По умолчанию кэш в памяти, воркер подставляет дисковый.
* `judge_submission(..., cancel=None, progress=None)`: `cancel()` опрашивается между шагами (бросает `JudgeCancelled`, вердикта нет);
  `progress(phase, done, total)` сообщает «compiling»/«running» и число проверенных тестов. Один тест не прерывается, он ограничен лимитами.
* Форматы задачи, протоколы чекера и интерактора не изменялись; все 60 прежних тестов проходят.
