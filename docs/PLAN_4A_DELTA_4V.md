## 2. Расхождения, которые нужно закрыть до продолжения

**Решено 2 ноября:**
- **К1** — режим «только группы»: контест по воле админа привязывается к группе и открыт её
  ученикам без кода. `open` остаётся четвёртым значением
  (`access_mode ∈ {open, code, groups, code_or_groups}`): ничего не стоит, на нём `practice` и `dev`.
- **К2** — вариант А: участие создаётся при первом входе, личный таймер — кнопкой «Начать» (Р21).
- **К3–К8** — приняты, как предложено ниже.

Ниже — исходные формулировки расхождений.

**К1. Режим `open`.** Дельта называет три режима: код/QR, только группы, оба. Сейчас есть ещё
`open` — контест виден всем ученикам, вход кнопкой; на нём сделаны `practice` и `dev`, и это
естественный режим для тренировочного архива «для всех».
- Вариант А: оставить четвёртым значением — `access_mode ∈ {open, code, groups, code_or_groups}`.
- Вариант Б: убрать; существующие `open`-контесты миграция переводит в `code`, архив для всех
  делается кодом или группами.

**К2. Личный таймер «при первом входе».** По Р21 таймер запускает кнопка «Начать», чтобы ученик
мог открыть контест заранее (прочитать правила) и не потерять время. В дельте: «запись об
участии и личный таймер создаются при первом входе».
- Вариант А: при первом входе создаётся участие, таймер — по-прежнему кнопкой «Начать».
- Вариант Б: таймер стартует при первом входе в контест в режиме `personal`.

**К3. Откат импорта и созданная им группа.** Группы не удаляются, а откат импорта означает
«как будто не было». Предлагаю: откат удаляет группу, только если она создана этим импортом,
в ней нет других учеников и она не подключена ни к одному контесту. Иначе он лишь убирает
учеников импорта из группы.

**К4. `note_md` видят ученики.** Считаю это пояснением преподавателя к заданию в контесте
(аналог «инструкций» в Classroom), видимым ученикам с доступом к задаче. Приватная заметка для
преподавателей, если понадобится, — отдельное поле позже.

**К5. Группы — часть `contest.yaml`.** `access: {mode, groups: [...]}`: аудитория — часть
описания контеста, `apply` остаётся идемпотентным. Убранная из YAML группа отключается
с предупреждением, как при смене `open` → `code`. Продления сроков в YAML **не** входят —
это оперативные действия (CLI и API).

**К6. Архивная группа не даёт доступа.** Её нельзя подключить к новому контесту; при архивации
judgectl и API показывают список контестов, где она подключена. Ученики сохраняют просмотр
своих посылок и оценок (правило из дельты).

**К7. Одно правило для картинок везде: PNG, JPEG, WebP.** GIF из пакета задачи отдаётся как
вложение. §5.7 (условие задачи, 4б) и 4в.3 (вложения) перестают расходиться.

**К8. Граница 4в и 4б.** 4в идёт до публичного API. В каждой сессии 4в: модель, сервисы,
правила доступа (чистые функции), админский API и judgectl. **Эндпоинты ученика — в 4б**, который
делится на 4б.1 (контесты, посылки, таблица, загрузка) и 4б.2 (ручные задания, комментарии,
вложения, материалы). Иначе каждая сессия 4в тянула бы за собой половину публичного API без его
общих правил (кулдауны, видимость, ограничение частоты).

### 3.3 Правила доступа (`access.py`, чистые функции)

**Доступ ученика к контесту** (кроме состояния `draft` / `archived`, как раньше):
- `open` — есть у всех (если режим остаётся, К1);
- код — есть, если у ученика есть участие с `joined_via = code`;
- группы — есть, если ученик **сейчас** состоит в неархивной группе, подключённой к контесту;
- оба — любое из двух.

Следствия:
- новый ученик группы получает доступ сразу, без действий;
- убранный из группы (или при отключении либо архивации группы, или при смене режима) теряет
  доступ к условиям и сдаче, но **всегда** видит свои посылки и оценки;
- участие создаётся при первом входе любым путём, с `joined_via`; само по себе доступ даёт
  только для пути «код»;
- админ видит всё, как раньше.

**Доступность задачи и сроки:**
- до `available_from` задача ученику не видна вовсе (ни метка, ни название);
- эффективный срок ученика = максимум из `due_at`, его личного продления и продлений групп,
  где он сейчас состоит; продление раньше базового срока отвергается;
- после эффективного срока:
  - условие — по `after_due_statement`;
  - сдача — по `after_due_submit`:
    - `no` — отказ `deadline_passed`;
    - `late` — принимается с `late = true`;
    - `yes` — принимается как обычная;
- окно контеста и правила дорешивания проверяются **раньше** срока задачи: закончившийся
  контест без дорешивания не принимает посылки, каким бы ни был срок задачи. Личный таймер
  и срок задачи действуют одновременно, побеждает более ранний;
- **границы:** `available_from` включительно; посылка в срок, если время приёма ≤ эффективного
  срока. Сверить с соглашением о границах окна контеста из 4а.2 и записать одно правило
  в CONTESTS.md;
- **время приёма** — серверное, в UTC, в момент получения запроса, до чтения тела (важно для
  больших загрузок в 4в.1);
- `late` фиксируется при приёме; продление, выданное позже, старые отметки не меняет.

### 3.4 judgectl и `contest.yaml` (4а.3a)

```

                   | add <группа> <логин>... | remove <группа> <логин>...
judgectl extension add <контест> <метка> (--user <логин> | --group <группа>) --due <время> [--reason]

                   | set-timezone <логин> <пояс|->
```

## 4. Изменения в 4а.4 (проверка задач эталонами)

Суть не меняется: задание воркеру «проверка версии» компилирует чекер и интерактор, прогоняет
эталоны и сравнивает вердикты, результат — `ready` / `failed` с `check_report`. Дополнения:

1. **Приоритет ниже посылок учеников.** Проверки задач не должны задерживать контест или урок:
   очередь берёт их только при отсутствии ожидающих посылок (или с отдельной квотой воркеров).
   В счётчике загрузки для учеников они показываются отдельно или не показываются.
2. **Повторная проверка:** `judgectl problem recheck <slug>@<v>` и
   `POST /api/admin/problems/{slug}/versions/{n}/recheck` — например, после смены версии
   компилятора.
3. **Понятные отказы:** `pin` и `contest apply` на версию в статусе `pending_check` или `failed`
   отказывают, указывая статус и где посмотреть `check_report`.
4. **Только задания с автопроверкой.** После 4в.1 проверка запускается только для версий задач;
   ручные задания и материалы версий задач не имеют.
5. **Тестовые пакеты:** сломанный чекер, эталон с неверным ожидаемым вердиктом, эталоны на TL,
   RE и CE (сейчас в примерах только OK и WA).

**Критерии приёмки 4а.4:**
- исправная задача становится `ready`;
- каждый из сломанных пакетов становится `failed` с отчётом, по которому понятна причина;
- во время проверки задачи посылки учеников не ждут дольше обычного (тест очереди);
- `recheck` работает;
- `pin` на `pending_check` или `failed` — понятный отказ.

После 4а.4 ветка `module-4a` сливается в master целиком.

## 5. План модуля 4в

**Общее для всех сессий:** этап 0 (план без изменений), этап = коммит, Alembic, тесты на
реальном PostgreSQL, docs в том же коммите. В каждой сессии: модель, сервисы, чистые функции
доступа, админский API, judgectl. Эндпоинты ученика — в 4б.2 (К8).

**Зависимости:**
- 4в.1 вводит `kind` у `contest_problems`, но `material` можно использовать только после 4в.4;
- таблица вложений 4в.3 ссылается на версии материалов, внешний ключ к ним добавляется в 4в.4;
- 4в.2 ни от чего, кроме 4в.1, не зависит.

Порядок 4в.1 → 4в.2 → 4в.3 → 4в.4 остаётся.

### 4в.1 — виды элементов контеста и ручные задания

- **Модель:**
  - `contest_problems.kind` (`problem` / `manual` / `material`), таблица **не**
    переименовывается;
  - `problem_version_id` становится nullable; CHECK по виду: у `problem` версия обязательна,
    у `manual` — нет;
  - `material` до 4в.4 запрещён CHECK-ом;
  - у `manual` — `title`, `statement_md`, `points` (nullable — без баллов, только статус).
- **Сдача:**
  - `submissions.kind` (`auto` / `manual`);
  - `submission_files` (`submission_id`, `path`, `blob_sha256`, `size`, тип по расширению);
  - текстовый ответ хранится как файл `answer.md`.

  Лимиты задаются в env: число файлов (10), размер файла (20 МБ), сумма на посылку (50 МБ).
  Каждая сдача — новая неизменяемая посылка; учитывается последняя, история видна.
- **Оценка:**
  - `manual_reviews` — только добавление строк, это и есть история: `status` (`submitted` /
    `in_review` / `returned` / `graded`), `score`, `reviewer`, `at`, короткий комментарий;
  - текущая оценка — последняя запись;
  - без очереди воркеров;
  - сроки, политики после срока, `late` и продления — общие с 4а.3.
- **Админский API и judgectl:**
  - очередь работ на проверку: фильтры по контесту, заданию, статусу, группе, `late`;
  - просмотр работы и скачивание файлов (по правилам отдачи файлов);
  - выставление оценки и возврат на доработку.
- **Критерии приёмки:**
  - нельзя создать `manual` с версией задачи или `problem` без неё;
  - ручная посылка никогда не попадает в очередь воркеров;
  - история оценок не теряется при повторной оценке;
  - срок и `late` работают так же, как у задач с автопроверкой;
  - лимиты файлов отдают 413 или 422 без чтения лишнего.
- **Вопросы этапа 0** (с моей рекомендацией): отдельная `manual_reviews` или строки
  `judgements` с особым источником — *рекомендую отдельную таблицу и общий сервис «текущий
  результат» для списков и таблицы в 4б*; может ли ученик отозвать сданную работу (как
  «Отменить отправку» в Classroom) — *рекомендую нет, вместо этого новая сдача*.

### 4в.2 — комментарии

- **Модель:**
  - `comment_threads`: на элемент контеста, вид `private` с учеником или `public`;
  - `comments`: автор, текст в Markdown, `created_at`, `deleted_at`, `deleted_by`;
  - `thread_reads`: `user_id`, `thread_id`, `last_read_comment_id` — так отметки о прочтении
    дёшевы и дают счётчик непрочитанного.
- **Правила:**
  - личная ветка — только ученик и преподаватели; ученики не пишут друг другу лично (такой
    сущности нет вовсе);
  - общая ветка по заданию по умолчанию выключена (флаг на элементе контеста) и всегда видна
    преподавателю;
  - писать могут только ученики с доступом к элементу; потерявший доступ видит свою личную
    ветку, но не пишет.
- **Санитизация и лимиты:**
  - сервер хранит исходный Markdown и проверяет длину (например, 4000 символов);
  - HTML в Markdown запрещён;
  - отрисовка — во фронтенде через санитайзер;
  - ограничение частоты на ученика (например, 10 в минуту);
  - журнал — `audit_log` для удаления и модерации.
- **Мягкое удаление:** ученик удаляет своё, преподаватель — любое; текст удалённого виден
  только преподавателям с пометкой. Правки сообщений — *рекомендую не делать* в первой версии.
- **Критерии приёмки:**
  - ученик не может прочитать чужую личную ветку ни через какой идентификатор (тест подмены);
  - общая ветка при выключенном флаге не принимает сообщения учеников;
  - удалённое не видно ученикам;
  - лимиты и частота работают;
  - счётчик непрочитанного верен.

### 4в.3 — вложения и ссылки

- **Модель:** `attachments` — ровно один владелец (CHECK): версия задачи, элемент контеста или
  версия материала (внешний ключ к материалам добавляется в 4в.4); плюс `blob_sha256`, имя,
  размер, тип по расширению, `position`, `created_by`. `links` — `url`, `title`, тот же набор
  владельцев.
- **Неизменяемость.** Вложения версии задачи объявляются в пакете (поле в `problem.yaml`)
  и создаются импортом: тогда они входят в `content_sha256`, и версия остаётся неизменяемой.
  Добавлять их потом через API нельзя. Вложения элемента контеста добавляются и удаляются
  в любой момент.
- **Отдача:**
  - всегда `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, CSP `sandbox`;
  - из картинок допустимы только PNG, JPEG, WebP, с проверкой сигнатуры файла на совпадение
    с расширением;
  - SVG и HTML отклоняются при загрузке;
  - остальные типы — по белому списку расширений (pdf, txt, md, py, c, cpp, h, csv, json, zip,
    docx, xlsx, pptx); исполняемые запрещены;
  - встроенный просмотр не делаем.
- **Ссылки:** только `http(s)`; сервер ссылки не открывает (никаких превью, никакого SSRF);
  фронтенд выводит их с `rel="noopener noreferrer"`.
- **Лимиты и квоты** задаются в env:
  - размер файла;
  - число вложений на объект;
  - квота на ученика — по логическому размеру его файлов (посылки 4в.1 и всё, что он
    загружает), несмотря на дедупликацию блобов.
- **Критерии приёмки:**
  - SVG, HTML и картинка с неверной сигнатурой отклоняются;
  - каждая отдача — `attachment` и `nosniff`;
  - квота блокирует загрузку сверх лимита;
  - вложение версии задачи меняется только новой версией.

### 4в.4 — библиотека материалов

- **Модель:**
  - `materials`: `slug`, название, `archived_at`, аудитория (`none` / `all_students` / группы);
  - `material_versions` — неизменяемые: Markdown и вложения 4в.3;
  - `material_tags`;
  - разрешается `contest_problems.kind = material` (ссылка на материал);
  - добавляется внешний ключ вложений к версиям материалов.
- **Ссылки из задач:**
  - `[[памятка:slug]]` в условиях и `references:` в `problem.yaml`;
  - при импорте задачи проверяется, что материал существует;
  - отсутствующий материал — ошибка импорта.
- **Доступ ученика к материалу** (решение из дельты): аудитория «все ученики» или его группа
  **либо** участие в контесте, где материал выложен или на него ссылается уже открытая
  (`available_from` прошёл) задача. Срок и скрытие условия доступ не отменяют. Архивный
  материал не показывается в библиотеке, но остаётся доступен по существующим ссылкам и
  выкладкам.
- **Вопросы этапа 0** (с моей рекомендацией):
  - какую версию показывает ссылка `[[…]]` — *рекомендую последнюю неархивную: памятки
    исправляют*;
  - закрепляет ли выкладка материала в контесте версию, как задачи — *рекомендую да, с явной
    сменой, для единообразия с `pin`*;
  - раздел «Справочник» — твой открытый вопрос, см. §7.
- **Критерии приёмки:**
  - импорт задачи с несуществующей ссылкой — отказ;
  - матрица доступа (аудитория × участие × открытость задачи × срок и скрытие × архив)
    проходит;
  - версии неизменяемы;
  - материал недоступен ученику без оснований из правила доступа.

## 6. Что меняется в 4б

- **4б делится на две части:**
  - **4б.1** — контесты, задачи, посылки, статусы, таблица результатов (с фильтром по группам),
    счётчик загрузки, профиль и часовой пояс;
  - **4б.2** — эндпоинты ученика для 4в: ручная сдача, комментарии, вложения, материалы.
- **Обязательства из 4а остаются:**
  - `read_one_moment()` перед `load_snapshot`;
  - серверная страховка для воркера «idle, но держит задание»;
  - отказ heartbeat после явного deregister;
  - картинки условия по §5.7 с учётом К7.
- **Тесты подмены идентификаторов на всех эндпоинтах ученика** — обязательный критерий 4б.1
  и 4б.2.

## 7. Открытые вопросы — решаешь ты

**В1. Ждёт ли пробный запуск готовности всего 4в?** Что следует из каждого ответа:
- **Да:** до пробного запуска добавляются 4 сессии 4в, 4б.2 и интерфейс для них в модуле 5.
  Ученики сразу видят полный набор возможностей, но первый запуск сдвигается заметно.
- **Нет:** пробный запуск после 4а → 4б.1 → 5 (только контесты) → 6, а 4в, 4б.2 и их
  интерфейс идут после. Раньше появится обратная связь по ядру (проверка, нагрузка, телефоны),
  но порядок «4в до 4б» тогда теряет смысл — 4в логичнее делать после запуска.
- Промежуточные варианты (например, только 4в.1 до запуска) тоже возможны; от ответа зависит
  порядок в ROADMAP.

**В2. Нужен ли у материалов раздел «Справочник»** — место, где ученик сам просматривает
материалы, вне контестов?
- **Да:** в 4в.4 добавляется признак «в справочнике» (или он совпадает с аудиторией «все
  ученики» / группой — это тоже нужно решить), выборка с тегами и поиском для 4б.2 и экран
  в модуле 5.
- **Нет:** материалы видны только через контесты и ссылки из задач; аудитория «все ученики»
  тогда означает только право открыть материал по ссылке.

Ответ нужен до этапа 0 сессии 4в.4, на 4а.3 он не влияет.
