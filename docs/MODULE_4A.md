# Модуль 4а: аккаунты, контесты, импорт задач, judgectl

Статус: сессии 4а.1 (аккаунты, сессии, 2FA, `judgectl` admin/user/queue/worker) и 4а.2 (импорт задач, контесты,
правила доступа, `judgectl` problem/contest/submission/status) **выполнены** (октябрь 2026, ветка `module-4a`;
миграции `c13b55a3e4d5`, `6bc3b8bd1c68`, `9e2f4a7c1b30`, `4d8a1c2e9f57`); 4а.3 (админский HTTP API) и 4а.4 (проверка
задачи воркером) впереди. Отступления от решений ниже и уточнения — в §5. Постоянные документы: `AUTH.md`,
`JUDGECTL.md`, `PROBLEM_IMPORT.md`, `CONTESTS.md`, `DATA_MODEL.md`.
Этот документ — спецификация модуля для Claude Code. После реализации
решения разносятся по постоянным документам (`AUTH.md`, `CONTESTS.md`,
`PROBLEM_IMPORT.md`, `JUDGECTL.md`, `DATA_MODEL.md`), а этот файл
остаётся как история решений.

## 1. Принятые решения

### 1.1. Роли и каналы управления

- **Р1. Две роли: `admin` и `student`.** Все администраторы (включая
  преподавателей) в веб-интерфейсе равноправны: пользователи, задачи,
  контесты, посылки, перепроверки. *Почему:* отдельная роль преподавателя
  не нужна — права одинаковые.
- **Р2. Консоль (`judgectl`) — канал владельца сервера.** Только через неё:
  создание и отключение администраторов, сброс 2FA администратора,
  токены воркеров, операции с очередью. *Почему:* скомпрометированный
  админский аккаунт в вебе не может создать себе сообщников или
  захватить воркеры; доступ к консоли = доступ к машине.

### 1.2. Учётные записи

- **Р3. Логин:** `^[a-z0-9][a-z0-9._-]{2,31}$`, хранится в нижнем регистре
  (`citext`; **уточнено в §5:** `varchar(32)` + `CHECK`), ввод обрезается и приводится к нижнему регистру.
  По умолчанию — транслитерация `фамилия.инициал` (`ivanov.p`), при
  коллизии добавляется цифра. Администратор может задать любой логин
  в этом алфавите (по просьбе ученика). *Почему:* латиница без пробелов
  не требует переключать раскладку на телефоне.
- **Р4. `display_name`** («Пётр И.») задаёт админ; только он виден другим
  ученикам в лидерборде. *Почему:* ученики — несовершеннолетние,
  полные ФИО наружу не показываем.
- **Р5. Пароли учеников генерирует система:** два коротких
  транслитерированных русских слова и число (`lisa-kot-472`), без
  неоднозначных символов. Показывается один раз, хранится только хеш.
  Смена пароля учеником — по желанию, не принудительно. *Почему:* легко
  набрать на телефоне; принудительная смена у детей = поток сбросов.
  Энтропия (~30 бит) достаточна при ограничении перебора (Р12).
- **Р6. Пароль администратора** задаёт он сам, не короче 12 символов.
- **Р7. Пачка учеников** — из CSV (`фамилия;имя[;логин][;display_name]`).
  Импорт сам определяет кодировку (UTF-8, UTF-8 с BOM, cp1251) и
  разделитель (`;` или `,`). Результат — CSV с логинами и паролями,
  права 0600. *Почему:* так сохраняет Excel на Windows.
- **Р8. Сброс пароля** — новый сгенерированный пароль, отзыв всех сессий
  и QR-токенов пользователя, снятие блокировки перебора.
- **Р9. Удаления пользователей нет** — только `is_active=false`
  (отзывает сессии). *Почему:* на пользователя ссылаются посылки.
- **Р10. Вход по QR (только ученики).** Админ выпускает одноразовый токен
  входа (срок 7 дней; новый токен отменяет предыдущий). Ссылка вида
  `https://<домен>/login/qr#<token>` — токен во фрагменте, поэтому не
  попадает в логи Caddy и в `Referer`; фронтенд отправляет его POST-ом.
  Карточки для печати (логин, пароль, QR) — данные отдаёт API в 4а,
  вёрстка карточек — модуль 5. Для администраторов QR-вход запрещён.

### 1.3. Сессии и безопасность

- **Р11. Серверные сессии в PostgreSQL**, не JWT. Cookie
  `__Host-session` (`HttpOnly; Secure; SameSite=Lax; Path=/`) с
  32-байтным случайным токеном; в БД хранится sha256. Время жизни:
  ученик — 30 дней без активности (скользящее); админ — 12 ч без
  активности, не более 7 дней всего. *Почему:* мгновенный отзыв, один
  сервер — преимущества JWT не нужны.
- **Р12. Перебор паролей.** Основной лимит — по логину (10 неудач за
  15 мин → блокировка на 15 мин, админ может снять досрочно), запасной —
  по IP, щедрый (класс в школьном Wi-Fi выходит с одного IP).
  Для администраторов лимит по логину строже (5 за 15 мин). Неудачи
  ввода TOTP считаются так же. Одинаковый ответ и время ответа для
  «нет логина» и «неверный пароль».
- **Р13. 2FA (TOTP) обязательна для администраторов** с первого дня,
  не в модуле 6. Вход админа двухшаговый: пароль → сессия в состоянии
  `mfa_pending` (TTL 5 мин, ничего не разрешает) → код TOTP → полная
  сессия. Подключение 2FA — при создании админа в `judgectl`
  (QR в терминале + `otpauth://` URI). Кодов восстановления нет:
  восстановление — сброс 2FA через консоль (Р2). Секрет TOTP хранится
  зашифрованным (Fernet, ключ `JUDGE_SECRET_KEY` в `/etc/judge/*.env`).
  Повторное использование кода в том же 30-секундном окне запрещено.
  *Почему:* админский вход открыт из интернета, а пароль — единственный
  рубеж без 2FA.
- **Р14. Хеширование паролей — argon2id** (`argon2-cffi`), перехеширование
  при входе, если изменились параметры.
- **Р15. CSRF:** проверка заголовка `Origin` + токен, привязанный к
  сессии, в заголовке `X-CSRF-Token` для всех небезопасных методов.
- **Р16. Один origin:** Caddy отдаёт фронтенд и проксирует `/api/*`.
  CORS не нужен.
- **Р17. Публичное приложение — отдельное ASGI-приложение на отдельном
  порту.** Caddy проксирует только его. `X-Forwarded-For` учитывается
  только от 127.0.0.1. *Почему:* Caddy тоже на localhost, поэтому
  внутренний API воркеров защищён прежде всего тем, что Caddy туда не
  проксирует; отказ внутреннего API от `X-Forwarded-*` — второй рубеж.
- **Р18. `audit_log`** для всех административных действий (веб и CLI);
  вход администратора тоже пишется. В админке показывается «последний
  вход: время, IP».

### 1.4. Контесты

- **Р19. Задачи выдаются ученикам только через контесты.** Тренировочный
  архив — контест без даты окончания.
- **Р20. Поля контеста:** `slug`, `title`, описание (Markdown),
  `starts_at`, `ends_at` (nullable), `scoring_mode` (`points` | `icpc`,
  штраф ICPC 20 мин), `leaderboard` (`hidden` | `visible` | `after_end`),
  `state` (`draft` | `published` | `archived`), `join_policy`
  (`open` | `code`) + `invite_code`, `allow_upsolving`, `languages`,
  `submit_cooldown_sec` (по умолчанию 15), `max_submissions_per_problem`
  (nullable), `tests_after_end` (показать все тесты после окончания),
  `plagiarism_enabled` (в 4а только флаг и описание интерфейса хука).
  Время — `timestamptz`, отображение в часовом поясе из настроек.
- **Р21. Режим времени `timing_mode`:**
  - `fixed` — общий таймер: окно `[starts_at, ends_at]` для всех;
  - `personal` — личный таймер: ученик в пределах `[starts_at, ends_at]`
    нажимает «Начать» (отдельно от вступления в контест), получает
    `personal_duration`; личный конец = `min(started_at + duration,
    ends_at)`. Штраф ICPC и «время решения» в таблице считаются от
    личного старта; `leaderboard=after_end` означает после `ends_at`.
- **Р22. Задачи контеста закрепляют версию** (`problem_version_id`).
  Новая версия задачи в контест сама не попадает; смена — явно
  (`pin`, в вебе и CLI) с предложением перепроверки. Закрепить можно
  только версию в статусе `ready`.
- **Р23. Подключение ученика:** после входа — список опубликованных
  контестов; `open` — кнопкой, `code` — по коду из 6 символов без
  похожих букв или по ссылке `/join/<КОД>` (QR на проекторе).
- **Р24. Приватность:** анонимного доступа нет. Ученик видит только свои
  посылки; чужие результаты — только агрегатами в лидерборде (по
  `display_name`), если лидерборд открыт и ученик — участник.
  Админ видит всё, включая все тесты.
- **Р25. Правила доступа — чистые функции** (`can_view_contest`,
  `can_submit`, `can_see_leaderboard`, `visible_tests`, `contest_window_for`)
  с отдельными тестами; эндпоинты 4б и админки вызывают только их.

### 1.5. Импорт задач

- **Р26. Один путь создания версии:** пакет → валидатор → каноничный
  манифест → блобы + `ProblemVersion`. Будущая веб-форма (модуль 5)
  собирает такой же пакет и идёт тем же путём.
- **Р27. Безопасная распаковка** (своя, не `extractall`): запрет
  абсолютных путей, `..`, симлинков и спецфайлов; лимиты на размер
  архива, распакованного содержимого, число файлов и коэффициент сжатия.
- **Р28. Валидатор формата — в общем пакете** рядом с `protocol/manifest.py`.
  Бэкенд не импортирует `runner`; это проверяет отдельный тест слоёв.
- **Р29. Повторный импорт:** задача определяется по `slug` из пакета;
  тот же дайджест манифеста → ничего не меняется («уже есть как vN»);
  другой → vN+1. Версии неизменяемы; удалить версию, на которую ссылаются
  посылки, нельзя — только архивировать задачу.
- **Р30. Статус версии** `pending_check` | `ready` | `failed`. Пока
  проверки через воркер нет, импорт ставит `ready` сразу; колонка
  заложена, чтобы 4а.4 не требовал перепроектирования.
- **Р31. `dev_seed.py` использует сервис импорта** (обязательство из
  модуля 3).
- **Р32. Проверка задачи воркером** (компиляция чекера/интерактора,
  прогон эталонных решений с ожидаемыми вердиктами) — сессия 4а.4,
  **если** формат и примеры содержат эталонные решения. Это проверяется
  на этапе 0 сессии 4а.1.

### 1.6. judgectl

- **Р33. Одна точка входа `judgectl`;** `admin_cli` переносится в группы
  `queue` и `worker`, старое имя — алиас до модуля 6. (Состав `queue` в 4а.1 — §5.)
- **Р34. judgectl работает через сервисный слой напрямую с БД,** не через
  HTTP. Аутентификация — доступ к ОС (запуск от `judge`, чтение
  `/etc/judge/*.env`). В `audit_log` — `cli:<unix-user>`.
- **Р35. Контесты декларативно:** `judgectl contest apply contest.yaml`
  идемпотентна; контесты можно хранить в git.
- **Р36. Вывод:** таблица для человека, `--json` для скриптов; пароли —
  один раз, пачка — в файл 0600.

```
judgectl admin    add | disable | enable | reset-password | reset-2fa | list
judgectl user     add | import <csv> | list | reset-password | disable | enable
                  | unlock | set-login | qr-token
judgectl problem  import <zip|dir> | list | versions <slug> | show | archive
judgectl contest  apply <yaml> | list | show | publish | archive
                  | pin <contest> <label> <version> [--rejudge]
                  | code regenerate | participants
judgectl submission show | rejudge (--id | --contest --problem | --problem-version)
judgectl queue    status
judgectl worker   list | token create | token revoke
judgectl status   # БД, живые воркеры, глубина очереди
```

### 1.7. Границы

- **4а:** миграции; сервисы (пользователи, сессии, 2FA, ограничение
  перебора, импорт, контесты, правила доступа); `judgectl`; публичное
  приложение с `auth/*`; **админский HTTP API** (для админского
  веб-интерфейса); при наличии эталонов — проверка задачи воркером.
- **4б:** API ученика (контесты, вступление, личный старт, условия,
  посылки, статусы, лидерборд, счётчик загрузки, кулдаун);
  `queue.read_one_moment()` перед `load_snapshot`; серверная страховка
  для воркера «idle, но держит задание»; отказ heartbeat-у воркера,
  снявшего регистрацию (нестабильный тест, §5.4); время в ответах API — в UTC (§5.4).
- **5:** интерфейс ученика (5а), админский веб-интерфейс и веб-форма
  задач (5б), печать карточек с QR.
- **6:** деплой (Caddy, домен `.ru`, systemd-юнит публичного приложения,
  заголовки безопасности), удаление dev-обёртки sudoers.

## 3. План сессий Claude Code

Общие правила (как в модуле 3): каждая сессия начинается в Plan mode
с плана без изменений в коде; этапы заканчиваются коммитом; на
**Стоп** — ждать подтверждения; схема БД — только через Alembic;
документация в `docs/` обновляется в том же коммите, что и поведение;
`sudo` в 4а не ожидается — если понадобится, остановиться и объяснить
зачем и какая команда; при сетевых ошибках сообщать о прокси, а не
повторять попытки.

### Сессия 4а.1 — аккаунты, сессии, 2FA

0. Прочитать `CLAUDE.md`, `docs/MODULE_4A.md`, `DATA_MODEL.md`,
   `PROBLEM_FORMAT.md`, код `admin_cli`. Выдать:
   (а) расхождения раздела 2 с текущей моделью;
   (б) **есть ли в формате и примерах эталонные решения с ожидаемыми
   вердиктами** (ответ определяет сессию 4а.4);
   (в) план этапов. **Стоп.**
1. Миграция: `users`, `sessions`, `auth_failures`/`auth_lockouts`,
   `login_tokens`, `audit_log`. Тесты миграции вверх/вниз на реальном
   PostgreSQL. Коммит.
2. Ядро безопасности: argon2id, генератор паролей и логинов
   (транслитерация, коллизии), сервис сессий, TOTP (шифрование секрета,
   защита от повторного кода), ограничение перебора, QR-токены.
   Юнит-тесты. Коммит.
3. Публичное приложение на отдельном порту: `POST /api/auth/login`,
   `POST /api/auth/totp`, `POST /api/auth/qr`, `POST /api/auth/logout`,
   `GET /api/auth/me`, `POST /api/auth/password`; CSRF; доверие к прокси
   только с 127.0.0.1. Тесты: флаги cookie; отказ без CSRF и с чужим
   `Origin`; блокировка после перебора и её снятие; `mfa_pending` ничего
   не разрешает; QR одноразовый и не работает для админа; сброс пароля
   отзывает сессии; через публичное приложение недоступен внутренний
   API. Коммит.
4. `judgectl`: каркас, группы `admin` (с QR для TOTP в терминале) и
   `user`, импорт CSV (UTF-8/BOM/cp1251, `;`/`,`), перенос `admin_cli`
   с алиасом. Коммит.
5. Документация: `docs/AUTH.md`, `docs/JUDGECTL.md`, обновить
   `DATA_MODEL.md` и `CLAUDE.md`. Коммит. **Стоп.**

**Готово, когда:** все тесты проходят на реальном PostgreSQL; от
пользователя `judge` создан админ с 2FA и 30 учеников из CSV в cp1251;
вход админа (пароль + TOTP) и ученика (пароль и QR) проходит через
`curl` с cookie и CSRF.

### Сессия 4а.2 — задачи и контесты

0. План. **Стоп.**
1. Миграция: `problems`, `problem_versions`, `contests`,
   `contest_problems`, `contest_participants`. Коммит.
2. Сервис импорта: безопасная распаковка, валидатор в общем пакете,
   дедупликация по дайджесту, версии, тест слоёв (бэкенд не импортирует
   `runner`). Тесты на вредоносные архивы (zip-slip, симлинк, бомба,
   слишком много файлов). `dev_seed.py` → сервис импорта. Коммит.
3. Сервис контестов: `apply` из YAML, `pin` (только `ready`),
   вступление по коду/открыто, личный старт, функции доступа (Р25) с
   тестами, включая оба режима времени и дорешивание. Коммит.
4. `judgectl`: `problem`, `contest`, `submission rejudge`, `status`.
   Коммит.
5. Сквозная проверка на реальной установке от `judge`: импорт всех

0. План. **Стоп.**
1. Каркас `/api/admin/*`: зависимость «только `admin` с полной

## 5. Отступления и уточнения

### 5.1. Сделано в 4а.1 иначе или точнее, чем в §1

- **Р3: `varchar(32)` + `CHECK` + `UNIQUE` вместо `citext`.** Логин и так хранится в нижнем регистре (ввод
  обрезается и приводится к нему при создании и при входе), поэтому `citext` (расширение БД) ничего не даёт.
  Миграция `c13b55a3e4d5` приводит существующие логины и останавливается со списком, если какой-то не проходит формат.
- **Транслитерация.** Упрощённая таблица (й→y, ё→e, ж→zh, х→kh, ц→ts, ч→ch, ш→sh, щ→shch, ы→y, э→e, ю→yu, я→ya,
  ъ/ь опускаются). **Инициал — транслитерация первой буквы имени целиком:** Ч→ch, Х→kh, Ш→sh, Щ→shch, Ж→zh, Ц→ts,
  Ю→yu, Я→ya (Подъячев Чеслав → `podyachev.ch`, Иванова Яна → `ivanova.ya`). Дефис сохраняется, пробел → дефис,
  апострофы и прочие символы выбрасываются. Полностью — `AUTH.md` §2.
- **Правила пароля, который выбирает человек:** ученик ≥ 8, админ ≥ 12, не больше 128, не пустой, не равен логину,
  не из списка распространённых.
- **Смена своего пароля (`POST /api/auth/password`):** текущий пароль, админу — ещё текущий код TOTP. Сначала
  проверяются правила для нового пароля (422; не неудача и не тратит код), затем блокировка (429), затем текущий пароль
  и код: неверные считаются неудачами входа этого логина и ведут к блокировке так же, как при входе (403
  `invalid_credentials`, сессия не отзывается). При успехе остальные сессии отзываются, текущая получает новый токен.
- **Р12, числа.** По логину 10 / 15 мин (админ 5) → блокировка 15 мин; по IP 300 / 15 мин → 15 мин; всё в env.
  Неудачи считаются и для несуществующих логинов; ответ о блокировке одинаков для существующего и несуществующего;
  при активной блокировке 429 даже с верным паролем. Блокировки — таблица `auth_lockouts` (не вычисляются из
  `auth_failures`): «снять» закрывает блокировку и добавляет строку-отметку, счёт начинается заново, история не удаляется.
- **Р13.** Админ без подтверждённой 2FA существует (`judgectl admin list`: `2FA = pending`), но войти не может;
  повторить подключение — `judgectl admin reset-2fa` (новый секрет с QR, отзыв всех сессий; без терминала отказ).
  Код, которым подтвердили подключение, для входа уже не годится (запрет повтора кода).
- **Р17.** Порты — из настроек (`JUDGE_PUBLIC_PORT` 8000, `JUDGE_INTERNAL_PORT` 8001); публичное приложение не
  стартует, если они совпадают, если `JUDGE_SECRET_KEY` пуст, равен заглушке `CHANGE_ME` или не ключ Fernet, или если
  `JUDGE_PUBLIC_ORIGIN` не голый `https`-origin (`http` — только для `localhost`).
- **Р18.** Колонки `audit_log` переименованы по §2 (`actor_user_id`, `at`, `ip`). Reaper `audit_log` не чистит.
- **Р33, состав `queue` в 4а.1:** `status | reap | judgements | events | rejudge` — всё, что было в `admin_cli`;
  `rejudge` пока со старыми флагами (`--submission` / `--contest-problem [--verdicts]`), в 4а.2 его заменит
  `submission rejudge`. `admin_cli status` = `queue status` + `worker list`; общий `judgectl status` — 4а.2.
  Команды `unlock` есть в обеих группах: `user unlock LOGIN | --ip ADDR`, `admin unlock LOGIN`.
- **Р32:** эталонные решения с ожидаемыми вердиктами в формате есть (`solutions: [{path, expect}]`, три примера из
  пяти) — **сессия 4а.4 нужна**. Для теста «сломанный чекер → `failed`» понадобится отдельный пакет.

### 5.6. Решено перед 4а.2: задачи и контесты

- **Миграция контестов:** `duration_minutes` задан → `timing_mode = personal`, `personal_duration` из него, иначе
  `fixed`; `leaderboard_enabled` → `visible` / `hidden`; `join_code` задан → `join_policy = code` (код сохраняется
  как `invite_code`), иначе `open`; `plagiarism_check` → `plagiarism_enabled`; `icpc_penalty_minutes` остаётся
  (по умолчанию 20); `freeze_at` остаётся, при `personal` запрещён (если такие данные есть — миграция
  останавливается со списком). Существующие контесты получают `state = published`; `starts_at` обязателен
  (`NOT NULL`), пустой заполняется `created_at`. `participations`: `joined_at = started_at`, `started_at` обнуляется
  в `fixed`-контестах.
- **`personal_duration`** — `interval` в БД, в YAML `90m` / `1h30m` / `2h`; должна быть > 0 (семантическая
  проверка). `timing_mode = personal` без `ends_at` разрешён (тренировка на время в бессрочном контесте).
- **`contest.yaml`:** схема `protocol/schemas/contest.schema.json`; `state` и `invite_code` в файле не хранятся
  (`contest publish|archive`, `contest code regenerate`; код создаётся при первом `apply` с `join_policy = code`;
  6 символов без похожих букв, ввод без учёта регистра); `join_policy` по умолчанию `code`. Время без смещения —
  в `JUDGE_TIMEZONE`; YAML читается без автоматического распознавания дат.
- **Задача в контесте определяется по задаче (`slug`), метка — изменяемый атрибут:** в `contest_problems` добавляется
  `problem_id`; задача и метка уникальны среди нескрытых строк (частичные индексы `WHERE NOT hidden`). *Уточнение
  этапа 2:* уникальность задачи тоже частичная, потому что `dev_seed` модуля 3 клал в контест `dev` по строке на каждую
  версию задачи; при переносе видимой остаётся последняя, прежние скрываются (их посылки сохраняются). Так же теперь
  делает `dev_seed`, когда появляется новая версия.
- **`apply` при смене `join_policy` с `open` на `code`** (уточнение после этапа 4) предупреждает, что снова действует
  прежний код приглашения (он сохраняется и при `open`), и подсказывает `judgectl contest code regenerate`; сам код в
  предупреждении и аудите не повторяется.
- **`contest_problems.hidden`:** `apply` для задачи, убранной из YAML, ставит `hidden`, если по ней есть посылки
  (ученики её не видят, в таблице её нет, посылки сохраняются), иначе удаляет строку; вернувшаяся задача снова видима.
  *Правило для этапа 4 (возвращение задачи при нескольких скрытых строках):* снова видимой становится **последняя**
  скрытая строка этой задачи, если её версия совпадает с версией в YAML или версия в YAML не указана; иначе создаётся
  новая строка (скрытые остаются скрытыми со своими посылками).
- **Версия в YAML:** номер; без номера — текущее закрепление, а при добавлении задачи — последняя `ready`. Если
  номер отличается от закреплённого и по задаче уже есть посылки — `apply` отказывает с подсказкой
  `contest pin … --rejudge | --no-rejudge` (Р22); без посылок меняет сам.
- **Р29, `content_sha256`** — по байтам всех файлов пакета (путь + sha256, отсортировано), включая условие и эталоны.
  Мусор не входит в хеш и не сохраняется: `.DS_Store`, `Thumbs.db`, `desktop.ini`, `*:Zone.Identifier`, `__MACOSX/`,
  `.git/`, `__pycache__/`, `*.pyc`, `*~`. Версии модуля 3 (созданные `dev_seed` без файлов) получают
  `content_sha256 = NULL`. Полный список файлов версии — `problem_versions.files jsonb {путь: sha256}`, каждый файл —
  блоб (картинки условия для 4б, выгрузка пакета, пересчёт хеша); исходный zip — по-прежнему `package_sha256`.
- **Р27, лимиты (через env):** архив ≤ 100 МБ, распаковано ≤ 512 МБ, ≤ 5000 файлов. **Защита от бомб — потоковый
  счётчик и лимит распакованного объёма** плюс ранний отказ по сумме заявленных размеров. *Уточнения после этапов 3 и
  4:* коэффициент сжатия (`JUDGE_IMPORT_MAX_RATIO`, на файл и в сумме) сначала был 100, потом 1000, теперь **0 —
  выключен** (настройка осталась): у deflate потолок около 1030, миллион однозначных чисел сжимается примерно в 1020
  и отклонялся бы. В архиве разрешены только методы **stored и deflate**; bzip2, lzma, deflate64 и шифрование —
  отказ с понятной причиной. Маски тестов: запрет `..` и абсолютных путей; результат `glob` после `resolve` обязан оставаться
  внутри пакета. `jsonschema` обязательна: без неё импорт — ошибка.
- **Схемы** `problem.schema.json` и `contest.schema.json` — в `protocol/schemas/` (на установку копируется только
  код); `docs/` ссылается туда.
- **Языки `python` / `c` / `cpp`** — единый источник `protocol/languages.py` (ключ и имя); его используют миграция
  4а.2 (вставляет недостающие строки `languages`) и `dev_seed`; тест сверяет ключи с `runner/languages.py:PROFILES`
  (бэкенд не импортирует раннер).
- **Передача пакета judgectl от `judge`:** `judgectl problem import -` читает zip из stdin. `python3 -m zipfile -c -`
  в stdout писать не умеет (проверено: создаёт файл с именем `-`), поэтому zip каталога даёт `tools/pack-problem.sh
  <каталог>` (тот же фильтр мусора, что у импорта).
- **Посылка в настоящий контест до API ученика (4б):** `dev_seed --contest <slug> --label <L> --user N` (только dev)
  проходит вступление, личный старт и `can_submit`; запускается через `j` (judge-dev не меняется).
- **Импорт в архивную задачу** — отказ с подсказкой `judgectl problem unarchive`. Добавляются также `problem
  unarchive` и `contest apply --dry-run`.
- **`problems.owner_id` может быть пустым** (уточнение этапа 3, миграция `9e2f4a7c1b30`): у импорта из консоли нет
  пользователя веба. Владелец — пользователь веба при импорте из веба (4а.3); `dev_seed` указывает `dev-teacher`.
  По той же причине пустым может быть `contests.created_by` (этап 4, миграция `4d8a1c2e9f57`).
- **Уточнения этапа 4 (правила доступа, `docs/CONTESTS.md` §4):** `freeze_at` нужен `ends_at`, он внутри окна и не при
  `leaderboard: hidden`; заморозка длится до `ends_at`, потом таблица живая; `archived` — только для чтения и только
  участникам; вступить после окончания можно только при `allow_upsolving`; лимит посылок считает только зачётные
  посылки, на дорешивание не действует; посылки админа принимаются всегда и в зачёт не идут.
- **Уточнения этапа 5 (judgectl):** `queue rejudge` и `admin_cli rejudge` — алиасы `submission rejudge` (старые флаги
  переводятся: `--submission` → `--id`, `--contest-problem` → `--contest-problem-id`); `--problem-version` пишется как
  `<slug>@<версия>` и перепроверяет посылки всех задач контестов, закреплённых на этой версии, включая скрытые;
  `contest pin` требует явного `--rejudge` или `--no-rejudge`; `problem import` и `contest apply` принимают `-` (stdin)
  и `--dry-run`; архивную задачу нельзя закрепить заново (`pin`), но контесты, где она есть, не меняются.
- **Блобы без ссылок** (файлы, записанные импортом, который потом не зафиксировался в БД) — известное ограничение;
  `judgectl status` показывает их число, не удаляя; `status --details` для строк без файла называет, кто на них
  ссылается (так отличаются остатки модуля 3 от пропажи новых файлов). Сборщик мусора блобов — модуль 6.

### 5.7. Решено перед 4а.3: админский HTTP API

- **Где и кто.** Префикс `/api/admin`, то же публичное приложение. Доступ — полная сессия (не `mfa_pending`), роль
  `admin`, активный пользователь; иначе 401 (`not_authenticated`, `mfa_required`) или 403 (`admin_required`). CSRF и
  Origin — как в `/api/auth`. Операций с админами (создание, отключение, удаление, сброс пароля и 2FA) и токенов воркеров
  в API **нет** (Р2); админ как объект виден только для чтения, любое действие над ним — 403 `admin_in_console`.
- **Единый формат ошибок** (и в `/api/auth`): `{"detail": "<код>", "message": "<текст для человека>"?, "problems":
  [...]?}`. Ошибки разбора тела — 422 `invalid_request` со списком `problems`; 404/405 — `not_found` /
  `method_not_allowed`. В `/api/auth/password` нарушение правил пароля — 422 `password_policy` + `message` (было: текст
  в `detail`).
- **Пагинация** — курсор по `id`, новые первыми: `?cursor=<id>&limit=<n>` (по умолчанию 50, больше 200 урезается до
  200), ответ `{"items": [...], "next_cursor": <id|null>}`. Поиск — `ILIKE` с экранированием `%` и `_`.
- **Время** — UTC с `Z`. Входящее время контеста — как в `contest.yaml` (без смещения — `JUDGE_TIMEZONE`).
- **Тело запроса.** JSON-эндпоинты — не больше 1 МБ, и по `Content-Length` (сразу), и для `chunked` (по счётчику):
  413 `too_large`, тело дальше не читается. Загрузки — сырое тело без `multipart`: `application/zip` для задач (лимит
  `JUDGE_IMPORT_MAX_ARCHIVE_MB`), `text/csv` для учеников (1 МБ); тело пишется потоком во временный файл со счётчиком,
  413 при превышении, 415 при другом типе. `import_package` принимает файл, а не байты; `judgectl problem import -`
  пишет stdin потоком во временный файл так же. `dry_run` поддержан.
- **Пароли и QR-токены** — только в ответах (`Cache-Control: no-store`, как у всего публичного приложения), один раз;
  в аудит и логи не попадают (тест проверяет и пароли, и токены, и коды TOTP).
- **Пользователи:** список с поиском и фильтрами (админы — только чтение), создание ученика, пачка из CSV (JSON с
  паролями, при `Accept: text/csv` — CSV как у judgectl, тоже `no-store`, имя файла в `Content-Disposition` без
  логинов), импорты и откат импорта (`confirm_import_id`), сброс пароля, вкл/выкл, смена логина, снятие блокировки
  (логина и IP), неудачи входа, удаление по правилам следов (`POST …/delete` с `confirm_login`), QR-токены пачкой на
  список учеников — одна запись аудита на пачку со списком id.
- **Задачи:** загрузка архива (`dry_run`; то же содержимое — 200 `exists`, не ошибка), список, версии (со `status` и
  `check_report`), карточка версии, файлы версии, архивация.
- **Файлы из загруженного контента** (файлы версии, исходник посылки) — защита от XSS: на всех таких ответах
  `X-Content-Type-Options: nosniff` и `Content-Security-Policy: sandbox; default-src 'none'`. В браузере (`inline`)
  открываются только картинки `png`, `jpeg`, `gif`, `webp` (*уточнено в 4а.3a, §5.8: без `gif`*) — тип **по расширению** из `files`, не по содержимому; всё
  остальное, включая SVG и HTML, — `Content-Disposition: attachment` и `application/octet-stream`; исходники и тесты —
  `text/plain; charset=utf-8` и `attachment`. `{path}` ищется **только среди ключей `files` версии**, без обращения к
  файловой системе по пути из URL. **Это же правило обязательно для картинок условия в 4б.**
- **Контесты:** создание и изменение — JSON по той же схеме, что `contest.yaml`, тем же `ContestSpec` и `apply`
  (`dry_run`, предупреждения); `publish` / `archive`, `pin` с обязательным `rejudge: true|false`, новый код,
  участники. Удаления контеста в 4а.3 нет (есть архивирование).
- **Посылки:** список с фильтрами (контест, метка, задача, пользователь, вердикт, статус), просмотр для админа
  (исходник — текст до 256 КБ или список файлов архива, сам исходник отдельным запросом; компиляция; все тесты, включая
  скрытые; история проверок) — запросы вынесены в общий сервис, `judgectl submission show` пользуется им же.
  Перепроверка — два шага: `dry_run` возвращает число затронутых посылок, подтверждение — тот же фильтр и `expect: N`;
  если число изменилось — 409 `count_changed`.
- **`GET /api/admin/system`:** очередь, воркеры, загрузка (`read_one_moment` + `load_snapshot`), проверка
  конфигурации, миграция; статистика блобов — только в консоли.
- **Ещё:** `GET /api/admin/audit` (фильтры, курсор; тест — в `details` нет паролей, токенов и кодов TOTP),
  `GET /api/admin/languages`. Ограничения частоты сверх CSRF и 2FA нет.
- **Все изменения** — в `audit_log` с `actor_user_id` и IP.
- **OpenAPI** по сети не отдаётся; `tools/gen-openapi.py` пишет `docs/openapi-admin.json`, тест сверяет файл с
  приложением. Описание — `docs/ADMIN_API.md`.
- Живая таблица результатов — не здесь (4б).

### 5.9. Сессия 4а.4: проверка версий задач эталонами через воркер

ТЗ — [`PLAN_4A_DELTA_4V.md`](PLAN_4A_DELTA_4V.md) §4, Р30 и Р32 выше; решения — D-048…D-056 в
[`DECISIONS.md`](DECISIONS.md). Там, где этот раздел расходится с §3 («Сессия 4а.4») и §1.5, действует он.

- **Задание — своя таблица `version_checks`** (статус, воркер, попытки, heartbeat, отчёт, `requested_by`), не вид
  judgement (D-048, миграция `b7e3d91a4c62`, [`DATA_MODEL.md`](DATA_MODEL.md)).
- **Приоритет** (D-049): двухфазная выдача — проверка только если этому воркеру не досталось посылки; одновременно не
  больше `JUDGE_MAX_CONCURRENT_CHECKS` (1). Справедливый порядок посылок не меняется.
- **Счётчик загрузки** (D-050): длина очереди и место ученика проверки не учитывают; воркер на проверке не входит в
  ёмкость; админ видит проверки в `/system` и `judgectl status`.
- **Импорт** (D-051): свой чекер, интерактор или эталоны → `pending_check` + задание; проверять нечего → `ready` с
  `check_report.reason = nothing_to_check`. Существующие версии остаются `ready`.
- **Воркер** (D-052): capability `problem_check`; компиляция чекера и интерактора, затем `selfcheck` эталонов;
  результат — `check_report` (по эталону: ожидалось, получено, совпало, первый неудачный тест, причина) и
  `ready` / `failed`. Эталоны приходят в задании, манифест не меняется.
- **Сбои** (D-053): `JUDGE_CHECK_TIMEOUT_SEC` (600) → `failed` с причиной; потерянные проверки — reaper, как посылки.
- **Перепроверка** (D-054): `judgectl problem recheck <slug>@<v>`, `POST /api/admin/problems/{slug}/versions/{n}/recheck`;
  статус меняется только по итогу; `failed` после перепроверки не снимает уже закреплённые версии, но о них
  предупреждают `/system`, `judgectl status`, `judgectl contest show`, `GET /api/admin/contests/{slug}`.
- **Отказы** (D-055): `pin` / `apply` на `pending_check` / `failed` — со статусом и местом отчёта; `apply` без версии —
  последняя `ready` с предупреждением.
- **Тестовые пакеты** — `tests/problems/check-*`: эталоны OK / WA / TL / RE / CE с верными ожиданиями (→ `ready`),
  сломанный чекер, сломанный интерактор, эталоны с неверным ожиданием (→ `failed`).
- **Принято на этапе 0 без вопроса:** «нет ждущих посылок» — для этого воркера; IE эталона → `failed`, сбой воркера →
  повтор; архивную задачу не перепроверяем; валидатор тестов не запускается; `dev_seed` (только dev) не ждёт проверки;
  `version_checks.requested_by` — след при удалении пользователя (§5.5).
- **Вид задания у воркера** (D-056, этап 4): `kind` проверяется явно, незнакомый — в лог и `release` по пути из
  задания, без выполнения; `SIGTERM` во время проверки возвращает её сразу, а не дорабатывает.
- **Поле `release` задания** (этап 5): воркер идёт по нему только как по относительному пути под
  `/internal/worker/v1/`; полный URL или выход за префикс — отказ с логом, токен никуда не уходит.
- **Приёмка 4а.4** (5 ноября 2026): все тесты, включая `tests/pg` на PostgreSQL 16; сквозной тест
  `tests/pg/test_problem_check_e2e_pg.py` — настоящий внутренний API (uvicorn) и настоящий `WorkerProcess` проверяют
  пакеты `tests/problems/check-*` и примеры (`check-verdicts`, `sum-of-two`, `pair-with-sum`, `guess-number` → `ready`;
  `check-wrong-expect` → `solution_mismatch`; `check-broken-checker` / `-interactor` → `*_compile_failed`); smoke
  `tools/smoke-admin-api.sh` на judge_test с `SEED_CMD` — `failures: 0, skipped: 0` дважды подряд; `sandbox-check` и
  `redteam` на isolate. Проверка на установке — по списку команд сессии.
